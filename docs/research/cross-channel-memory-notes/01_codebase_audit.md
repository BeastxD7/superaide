## 1. Identity: how one human is resolved across channels

### Takeaway
A human is a `Person`; each platform account is a `ChannelIdentity` keyed by (provider, tenant_scope, stable_key). Only linked, active, non-external identities resolve to a Person; everything else is a "stranger" with fixed replies and no memory. Linking happens only by an app-issued invite/code, never by name. There is no automatic merge of identities and no Person for an unlinked colleague or client.

### Cited Findings

### Inferences
- The only identity key across channels is Person. A colleague or client who has not been linked by the owner is just an unlinked ChannelIdentity per platform: Ava cannot tell that Slack-U123 and Telegram-555 are one non-owner human, and there is no "known external party" Person unless the owner creates a Contact and links an account.
- The Slack identity is per (sender's team, user id), so one human in two workspaces is two identities.

### Gaps
- No identity for "client from another organisation" that can be trusted at any level: external flag hard-blocks person resolution (resolver.py:100-101), so such a user can never be a known Person even if the owner wanted them to be.
- Did not verify identity/claims.py internals or the operator `add-manager/add-colleague` CLI beyond what the pipeline calls.

## 2. Contexts, events, audience

### Takeaway
One `Context` per platform conversation id (DM channel, channel id, Telegram chat) and one `Event` row per message in/out with a per-event audience snapshot. Threads are not Contexts: they are `Event.thread_id` within the channel's Context. The audience gate treats every non-DM context as having unknown members, so in any channel or thread the only memories visible are `allowed_kind = "public"`, even for the verified owner.

### Cited Findings
- `Context` db/models.py:147-156: unique (agent_id, provider, tenant_scope, external_id); `kind` dm|group|thread|meeting (only dm/group are ever written from channels: kind = `msg.chat_kind`, memory/store.py:42-49); `audience_class` private_1to1|team|mixed_external; title. Context key is `external_id = msg.chat_id`; `tenant_scope` = "" for Telegram else `raw.team_id or tenant_scope` (workspace that received the event, store.py:64-66). So: Slack DM = one Context per DM channel id (D…); a channel = one Context per channel id; **a thread has no Context row** (it shares the channel's). Web = `web:<person id>`.
- `Event` db/models.py:159-188: context_id, direction in|out, sender_identity_id, resolved_person_id, trust_at_time, `audience_person_ids[]`, `audience_has_unknown`, content, `meta` JSONB (sources, activity, reasoning, kind e.g. triage/digest, other_channels, undelivered), webhook_verified, `external_id` (platform message id), `thread_id`. Unique index on (context_id, external_id) for inbound only :164-170 (redelivery drop); index (context_id, thread_id); GIN FTS on content :172.
- Thread bookkeeping: inbound events are logged with `thread_id = msg.thread_id` (pipeline.py:162-165) but replies with `thread_of(msg)` (pipeline.py:82-89, 763): for a Slack channel @mention with no thread the reply goes into a new thread rooted at that message (`thread = msg.message_id`). `recent_events()` memory/store.py:115-128 returns the last 12 events of the Context for a thread (`thread_id == t OR external_id == t`, so the root message is included) or, outside threads, only events with `thread_id IS NULL`. Top-level @mentions therefore build one "main" history per channel (inbound only; replies are in threads), and each thread has its own.
- `Audience` dataclass context/audience.py:25-37 (person_ids, has_unknown, min_trust, all_internal). `audience_for()` :40-51: **only `context.kind == "dm" and sender.known` yields a known audience** (`{person}`, has_unknown False, min_trust=sender.trust, all_internal = relation in manager/colleague). Everything else (strangers, external, any group/channel/thread) yields `Audience(person_ids={sender if known}, has_unknown=True, min_trust=0, all_internal=False)`. The other participants of a channel are never enumerated; only the current sender's id is recorded.
- `memory_filter()` audience.py:54-73 (SQL): `public` OR (`org` AND not has_unknown AND all_internal) OR (`persons` AND not has_unknown AND person_ids non-empty AND `allowed_person_ids @> audience`), AND (`min_trust <= aud.min_trust`, or, if has_unknown, `allowed_kind == "public"`), AND not expired (`valid_to`), AND `conflict_status == "none"`. `visible_memories()` :82-88 = newest N matching (5, or 30 for owner), by created_at desc, no relevance.
- Event audience snapshot written by `log_event` memory/store.py:69-98: `audience_person_ids = sorted(aud.person_ids)`, `audience_has_unknown`. In a channel each message's audience is just its own sender and has_unknown=True; Ava's reply is logged with the same sender-derived audience (pipeline.py:763).
- Message recall gate context/recall.py:218-226: `Event.audience_person_ids @> aud.person_ids`, direction "in" only; returns [] when `aud.has_unknown`. **The event's own `audience_has_unknown` is not checked** in this gate (contrast `owner_timeline`, which requires `== [owner]` and `has_unknown False`, memory/store.py:166-172). Consequence: the owner's own @mentions in channels (audience [owner], has_unknown True) are returned by recall in the owner's private DM (they are the owner's words, so harmless). Colleague/client channel messages carry [colleague] only, so they never match an owner audience: **the owner cannot recall what colleagues said** (INFERENCE from the two gates).
- Cross-channel timeline (ADR 0008 WP1) `owner_timeline()` memory/store.py:147-194: only for the owner's own private DM (`_owner_turn`); adds up to 12 events from other DM contexts within 48 h, SQL: `Context.kind == 'dm'`, `audience_person_ids == [owner]`, `has_unknown False`, `resolved_person_id == owner OR direction == 'out'`, same agent; labelled `[On Telegram · Wed 19:13]` via `WHERE` map :137; ~8,000 chars budget (TIMELINE_CHARS), 600 chars/event. Never used in groups.
- Prompt history for non-owner/group turns: `build_messages(recent_events(ctx, thread))` pipeline.py:678 and brain/turn.py:131-164: every `in` event becomes role "user" with consecutive user turns concatenated by newline. **No speaker name/id is attached to any turn**, so in a channel the model cannot tell which person said what, and the earlier events of every participant in that thread are shown to everyone in it (same Context/thread, so same audience by construction).
- What each prompt may see:
  - Owner private DM (any channel, `_owner_turn` pipeline.py:599-672): system = charter + OWNER_RULES, "You are talking to your owner... never doubt it's them" (brain/loop.py:400-461), brief with preferences/quiet hours/never_share/contacts/pinned facts (knowledge/profile.py:90-120, core_facts :54-77 max 15 facts/1,600 chars, categories preference+about, filtered by memory_filter), pre-recall notes (loop.py:729-745, strict AND, 4 notes), the cross-channel timeline, tools (recall, reminders, calendar/gmail, web, propose_action). Recall tool = notes + messages + document chunks under the DM audience (recall.py:273-298).
  - Anyone else, and the owner in any group/thread (`_think` pipeline.py:674-718): single structured call, no tools, no recall, no learning. System = charter + RULES + "Who you are talking to: {name}. Relation: {relation}. Trust tier: {n}. This is {audience.describe()}." + `owner_brief` + "Memories you may use here: ..." (turn.py:60-74). For a group `describe()` = "a conversation that includes people you cannot verify" (audience.py:32-37). Memories = `visible_memories` limit 5 (30 if `is_owner`, but gate still public-only in groups). `is_owner` there = relation manager and audience == {self} (pipeline.py:675), true for the owner in a channel too.
  - `owner_brief` for non-owner / owner-in-group (profile.py:122-154): "You work for {owner}", "You may tell this person: {shareable labels or 'nothing about them beyond their name'}. Everything else about your owner is private, whoever asks...", availability line, and Contact relationship if the sender is the owner's Contact. The `never_share` text is NOT included (profile.py:122-125; the CLAUDE.md "top-priority leak" is fixed on main). Note `private = audience.person_ids == {owner.id} and not aud.has_unknown` (profile.py:87), so the owner in a channel gets this stranger-style brief.

### VERIFIED TRACE (from coordinator): owner linked in DM, then "@Ava now?" in a channel thread
Chain confirmed in code:
1. Identity: `redeem_invite` linked the Slack identity (trust_level 2, endpoint_key `T0A4RGC1V70/A0CCGP11A1E`, last_seen_at set) accounts.py:240-244. The model sees the owner as relation manager but a context of unverifiable people, with no sentence that the sender is the verified owner (contrast the owner-turn prompt, loop.py:410-415). 6. History: `recent_events(ctx, thread_id=thread)` (pipeline.py:678) returns the last 12 events of that thread. Earlier stranger-mode replies ("I don't recognise this account yet...", `_stranger` :551-555; logged as `out` events in that thread by `_reply` :763 with `thread_of`) stay in the thread, are rendered as assistant turns (turn.py:139-155) and nothing marks them as stale after linking. They prime the model to repeat the stance.
7. Halt word works in any context for a known manager (pipeline.py:178-184). `remember ...` shortcut only works in DMs (:271). Linking by code in a channel is refused (:327-331).
- Also note: in the unconfirmed state (`sender.unconfirmed`) in a non-DM context pipeline returns without any reply (:224-225), so silence, not the "can't confirm" text, is the code path for that case; the thread reply therefore came from `_think`, consistent with the trace.

### Inferences
- A group/channel audience is never computed as a set of people; it is a boolean "unknown". There is no per-context participant list, no channel membership lookup, no "who is in this thread" record other than the senders of events.
- Because `Event.audience_person_ids` in a channel is only the sender, "everyone who saw this message" is not recoverable from the event log; ADR 0008's rule "event audience == [owner]" works only because channels are excluded by `has_unknown`.

### Gaps
- Slack `conversations.members`/channel membership is not fetched anywhere I looked. Nothing records which people were present in a channel.
- Did not read channels/runner.py endpoint plumbing or reception/service.py in detail.

## 3. Memory

### Takeaway
All durable memory is `MemoryItem`, almost exclusively facts about the OWNER learned only from the owner's own DM messages (plus documents/links/passports/connector facts). What a colleague says is stored only as raw `Event` rows (and, for the "remember ..." command in a DM, a note visible only to that colleague). There is no per-person note about third parties, no group memory, and no memory written from channel traffic.

### Cited Findings
- `MemoryItem` db/models.py:194-251 (columns on main): content; `subject_person_ids[]`; `source_event_ids[]`; `origin_context_id`; audience = `allowed_kind` persons|org|public + `allowed_person_ids[]` + `min_trust` (default 2); `valid_from/valid_to`; `category` (about|work|person|preference|urgency|availability|sharing|other); `source` (chat|intro_chat|intro_call|document|link|telegram|slack|owner_edit|gmail|calendar, knowledge/store.py:24-35); `document_id`, `source_document_ids[]`, `chunk_id`; `confidence`; `lease_id`; `import_id` (passport); `belief_state` fact|hearsay; `importance`, `time_bound`; `last_verified_at`, `verify_count`, `recheck_asked_at`; `trust_rank` (1 owner verified ... 5 other web, knowledge/trust.py:10-14, 16-27); `author_person_id`; `superseded_by`; `conflict_status` none|pending|review|resolved; `conflicts_with_id`; `source_ref` ("calendar:<id>", "gmail:<id>"). No `locked` column and no `origin_author` column exist (the latter is only a parameter to `remember_fact`, store.py:90, used for the Echo root). Embeddings live outside the ORM in `memory_embedding` (ADR 0008 as-built).
- `MemoryOrigin` db/models.py:254-261: one row per (memory_id, origin_root); used by the Echo Filter.
- Echo Filter memory/echo.py: counts independent root origins (quote chain > canonical URL > author); `HEARSAY_SOURCES = {link, telegram, slack, gmail}` :26; two roots promote hearsay -> fact; **off by default** (`echo_filter_enabled: bool = False`, config.py:305). Note "telegram"/"slack" are hearsay sources, though in practice the only telegram/slack-sourced facts written are the owner's own words (INFERENCE: with the flag on, the owner's own Telegram statements would become hearsay; I did not test this).
- Extraction: `knowledge/learn.py` job `learn_from_turn`, scheduled only in the owner-DM branch (pipeline.py:302-304; `worth_reading` learn.py:45-54, 25-char minimum except first-person stances). The extractor (`knowledge/facts.py extract_facts`, small model, inside spend cap) gets the owner's message plus 5 neighbour facts (`neighbours` :132-140), returns facts with category/importance/time_bound/`same_as`/`replaces`. Merge into an existing same fact only if its audience is exactly [owner] (:101-110, 126-129); else `remember_fact` (knowledge/store.py:78-145) which sets `subject_person_ids=[owner]`, `allowed_kind persons`, `allowed_person_ids=[owner]` (or public if `shareable`), `min_trust 2`, dedupe by `find_same_fact` (normalised equality or trigram >= 0.8), `supersede()` (store.py:148-164: newer retires older only if its trust_rank <= older's; else it becomes `pending` conflict for the owner). Docs/links go through `knowledge/ingest.py`/`extract.py` (not re-read in full); connector facts `connector_facts.py`; calendar/Gmail are looked up live, not stored (ADR 0008 addendum).
- `memory.store.remember()` memory/store.py:217-260: the "remember that ..." DM shortcut (pipeline.py:270-283). Subject = the speaker, `allowed_person_ids = audience (the speaker alone)`, min_trust 2, `trust_rank` 1 for owner, 4 (THIRD_PARTY) for a colleague. **A colleague's remembered note is visible only to that colleague in a DM**; the owner's audience `{owner}` is not contained in `[colleague]`, so the owner's recall cannot see it, and nobody in a channel can. Dedupe via `lexicon.normalise` (:211-214).
- The model never writes memory tables directly. Its only side-effect channel is `requested_action` / `propose_action`, gated by `policy.actions.decide`.
- Owner brief `profile.owner_brief` described in section 2 (owner-private branch: settings, contacts, up to 15 pinned `preference`/`about` facts; non-owner branch: shareable labels + contact relationship).
- Recall (`context/recall.py`): notes (AND, OR, trigram arms, + embedding "meaning" arm from context/vectors.py, RRF k=60, times importance/decay weight, :84-146), messages (inbound only, :222-257), document chunks (:188-215), `channel` filter (:36, 260-270); `pre_recall` strict-AND before the owner model call (:322-329). Gate = `memory_filter(aud)` inlined in each arm; messages require `event.audience_person_ids @> aud.person_ids` and `not aud.has_unknown`; chunks require the owner alone, trust >= 2 (:167-174).
- Episodes (`Episode` db/models.py:264-283, `memory/sleep.py`): nightly, off by default (`SLEEP_JOB_ENABLED`); cuts events where `audience_person_ids @> [owner]` into episodes (6 h gap), keeps intersection of audiences and `audience_has_unknown = any(...)` :77-95, 125-165; summaries by code or small model. **Episodes are written but I found no reader**: recall.py, loop.py and the memory skill do not query `Episode` (grep for "episode" in those files returned nothing). `ConsolidationRun` + `tidy()` merge duplicate owner notes, retiring at most 25% with a restorable snapshot. Other lifecycle: `knowledge/recheck.py` (spaced "is this still true?"), `memory/importance.py` (decay for time_bound), `imports` passports (`MemoryImport`), erase (`knowledge/erase.py`).
- Per-person notes about third parties: `Contact.notes` (<=1000 chars, owner-written), `Contact.relationship/vip`. `category = "person"` facts are still `subject_person_ids=[owner]` (remember_fact always sets the owner as subject). No table or column stores "what Ava learned about colleague X" with X as subject, and nothing learns from a colleague.
- What is stored when a colleague (not the owner) speaks: (a) `Event` row in/out with audience [colleague] (DM) or [colleague]+has_unknown (channel) pipeline.py:162-165; (b) `ChannelIdentity.last_seen_at`; (c) shadow `triage` bookkeeping when `triage_enabled` (`_shadow_triage` :376-387, ADR 0010); (d) time-travel rule firings when enabled (:169-176); (e) the `remember` note described above; (f) audit rows. No `learn_from_turn`, no memory from channel messages. `learn.py` docstring states this is deliberate: "third-party messages are where memory poisoning comes from" (learn.py:1-7).

- `Episode` is dead storage today.

## 4. Scenarios: what Ava does today, and where it breaks or leaks

### (1) Owner DMs Ava about issue X, then asks in a team channel "@Ava what do you know about X?"
Trace: DM -> `_owner_turn`; `learn_from_turn` stores owner-only facts (`persons`, [owner]). Slack message in the channel arrives only as `app_mention`; Context kind group; `audience_for` -> has_unknown, so `visible_memories` returns public notes only; reply via `_think` (no recall tool, no pre-recall, no timeline, owner brief in stranger form). Ava will say she has nothing (or that she cannot verify the speaker, as in the verified trace). **Today it is safe (no leak) but unusable**: the verified owner gets stranger treatment. Nothing from the DM (facts, events, timeline) crosses. The owner's @mention is itself logged (audience [owner], has_unknown) but not learned. Also (INFERENCE) if the owner had previously marked a fact `shareable` (public) it would appear: that is the only path, and it exists only via knowledge/profile and `remember_fact(shareable=True)`.
Design break: no concept of "owner-level but audience-limited" disclosure; the model gets no owner identity statement; no way to answer from private memory with consent ("shall I share this here?"); no per-fact "channel-shareable" state beyond public.

### (2) A colleague tells Ava something in DM, then mentions it in a channel
DM: known colleague, not owner -> `_think` with DM audience {colleague}: sees `public`, `org` (all_internal for colleague/manager) and persons-notes whose `allowed_person_ids @> [colleague]`; no learning, no tools. If they say "remember that ...", `remember()` stores a rank-4 note allowed only to them. The channel mention: group audience -> public only; recent_events of the channel thread do not include their DM (different Context). So Ava has no knowledge of the DM in the channel (safe), and the colleague's DM content never reaches the owner (no escalation channel besides triage shadow/digest when enabled, ADR 0010), nor can the owner's recall see it (audience mismatch). Note `org` memories (visible to any known internal person in a DM) are the only shared-by-default knowledge for colleagues, and are not created by the learn path I read (learn creates `persons`/`public` only; `allowed_kind="org"` writers not found, INFERENCE: org is read-only in practice).
Break: a colleague cannot teach Ava anything that persists for others; things they say are not attributed or promoted for the owner to review.

### (3) A client from another organisation asks in a shared (Slack Connect) channel
`user_team != our_team` -> external flag; identity separate (tenant_scope = their team); `resolve()` forces person=None; stranger branch: `claims.review` only for DMs; `handle_stranger` (receptionist) only for DMs per its comment ("None: off, not a DM") else `_stranger()` fixed reply with the AI notice, replied in a thread under their message; Context.audience_class -> mixed_external (stored only). No model call, no memory. Their message is logged with audience [] has_unknown. Safe, but (a) Ava is mute-by-script to clients in channels (cannot help from public info), (b) the fixed reply tells them to "open the link from Connections in the app" which is meaningless for a client, (c) the channel's Context is shared with internal members, so after one external message the whole Context is `mixed_external` (a one-way flag, memory/store.py:59-60) but the gate already treats every channel as unknown, so there is no change in what is shown. Group `recent_events` shows the client's text to the next sender's prompt only inside the same thread/channel (same audience by construction), without speaker labels.

### (4) Telegram and web with the same owner
Both are owner DMs of one Person (identity trust 2; web created at hire). `owner_timeline` merges the other DM contexts' last 48 h (max 12 events, labelled); learning is shared; recall spans channels (messages filter on audience only, not on provider unless `channel` passed). Works (ADR 0008 as built; tests/pipeline/test_cross_channel_scenario.py). Caveats: only DM contexts with audience exactly [owner] qualify (so a Telegram *group* with the owner never contributes); the timeline is 48 h; if the Telegram identity goes `unconfirmed` (new bot or after `link_reconfirm_after_days`) the owner is treated as a stranger on that channel (fixed reply; in a group, silence, pipeline.py:219-228); Web has no thread concept.

### (5) A thread continuing for days
History = last 12 events of that thread (`recent_events`), no time window, no summary, no episode usage; the model sees stale assistant turns (including stranger replies) as its own. `gap_line` markers are only added for owner turns (`tz` passed only from `_owner_turn`; `_think` calls `build_messages(recent_events(...))` without tz, pipeline.py:678). Sleep-job episodes are not read. No link from a thread to facts learned later (nothing is learned from threads). After a link/role change, old events keep `trust_at_time` and audience snapshots as of then (by design for audit), but the model-facing history does not reflect that.

### (6) Channels where Ava sees messages only when @-mentioned
Slack: plain channel messages are dropped at parse time (slack.py:81-82), so Ava has zero context of the conversation around the mention; she sees only the mention text (with raw `<@U…>`), plus earlier mentions/replies in that Context and thread. If a thread's other participants reply without mentioning her, those replies are never stored (not even as events). Her history in a thread is therefore her own turns and mentions only, with no sender labels, so "summarise this thread" is impossible. No `conversations.history`/`replies` fetch exists (INFERENCE from code read; not an exhaustive grep). Telegram groups: the adapter forwards whatever the bot receives (privacy mode, if on, restricts to commands/mentions: platform setting not visible in code) and records them all as events with audience [sender]+has_unknown, but none of it is learned.

### Cross-cutting breaks and leak surfaces found
- B1 (the verified bug): a verified, linked owner in any non-DM context is treated as an unverifiable audience; routed to `_think`; no private memory, no tools, stranger-style brief, no statement of owner identity; stale stranger replies remain in thread history.
- B2: no speaker attribution in group history (turn.py:139-155) and the model sees up to 12 turns from several people merged as one "user".
- B3: `audience_class`, `Context.kind` thread/meeting are unused by the gate; `Context` has no participant/member data.
- B4: recall_messages event gate ignores the event's `audience_has_unknown` (recall.py:218-219); today harmless because only owner-own messages match an owner audience, but it would become a leak if group audiences ever carried multiple person ids (INFERENCE).
- B5: `visible_memories` is "newest N", not relevance-ranked (audience.py:82-88) and used for every non-owner turn; owner turns use recall/pre-recall instead.
- B6: `Episode` unread; `org` audience has no writer (INFERENCE); Echo Filter off by default; `locked`/`origin_author` columns do not exist.
- B7: ADR 0008 deliberately excludes groups from every cross-channel mechanism ("anything into a group: never"); a redesign that lets the owner's private memory inform a channel answer changes that decision and must say so.
- B8: no mention-only rule on Telegram; Slack mention text not normalised.
