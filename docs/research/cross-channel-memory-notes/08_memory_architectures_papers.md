# Memory architectures for long-term and multi-party conversational memory: primary-paper evidence (as of 2026-10-23)

Method note: every paper below was downloaded as PDF from arxiv.org/pdf/<id> and converted to text locally; numbers are copied from the tables named. "Vendor-reported" is marked where the authors sell the system being measured. Where a number comes from a paper other than the one that owns the system, that is stated. Nothing here is from abstracts or search snippets unless it says "snippet only".

Short reading guide for the report writer: the three papers that matter most for a multi-party assistant are GroupMemBench (2605.14498), EverMemBench (2602.01313) and SpeakerMem-R1 (2609.26780). Their central, replicated-across-papers result is that raw, speaker-labelled message text retrieved with BM25 matches or beats most "memory systems" (Mem0, A-Mem, MemGPT, GraphRAG) in group chats, and that the bottleneck is retrieval/attribution, not the answering model.

## 1. What unit of memory works best (turn, session, segment, fact, episode, graph edge)?

### Takeaway
No single unit wins everywhere, but the evidence converges on: keep the raw message/turn (with speaker and thread metadata) as the ground-truth unit, retrieve at turn/round or topic-segment level, and treat extracted facts only as an additional index key (document expansion) rather than a replacement. Replacing raw text with summaries or facts loses information on detail questions; in group chats, fact extraction measurably loses speaker and thread structure.

### Cited Findings
- LongMemEval round vs session vs facts (GPT-4o reader, Fig 5, no numbers in text): "decomposing sessions into rounds significantly enhances reading performance with GPT-4o ... replacing sessions or rounds with extracted summaries or facts negatively impacts QA performance due to information loss. The only exception is with multi-session reasoning questions, where fact decomposition consistently improves performance." — [2410.10813 Sec 5.2](https://arxiv.org/abs/2410.10813)
- LongMemEval key expansion, Table 3 (LongMemEval-M, GPT-4o reader, top-10): Round K=V 0.670 accuracy vs Round K=V+fact 0.720; Round K=fact alone 0.664; Session K=V+fact 0.700 vs K=V 0.676; Session K=summary alone 0.554 (top-5) and 0.252 (top-10; the top-10 cell is anomalously low and not explained in the text). Recall@5 Round K=V 0.582 vs K=V+fact 0.644. Authors: condensed forms alone "does not enhance the memory recall performance"; adding facts to the original text gave "an average improvement of 9.4% in recall@k and 5.4% in final accuracy". Rank-merging separate indexes (Table 10) was worse than merging into one key (e.g. Round K=V+fact RM top-10 GPT-4o 0.596 vs KM 0.720). — [2410.10813 Sec 5.3, Tables 3 and 10](https://arxiv.org/abs/2410.10813)
- LongMemEval index keys used only the user-side utterances when sessions/rounds were keys: "When sessions or rounds are used as the key, we only keep the user-side utterances." — [2410.10813 Sec 5.1](https://arxiv.org/abs/2410.10813)

### Inferences
- **What we should copy:** (a) store every message verbatim with immutable speaker id, platform, thread/reply-to id, timestamp, audience; (b) make the retrieval unit the message or a short topic segment (a few turns around a reply chain), not a whole day/session; (c) add extracted facts only as extra index text appended to the raw text key (LongMemEval "K = V + fact"), never as the only record; (d) keep derived person-level/group-level notes as a second track with provenance links to the raw ids (SpeakerMem-R1 pattern).
- **What the numbers do not show:** SeCom's gains are on LoCoMo/Long-MT-Bench+ (dyadic, short, GPT4Score judged); segmentation quality depends on the segmenter (GPT-4 71.57 vs RoBERTa 61.84 vs turn-level BM25 65.58, so a weak segmenter is worse than no segmenter). LongMemEval's "round" value excludes assistant turns from the key, which is not directly transferable to group chats where all participants speak. No paper tests segmentation on interleaved multi-thread group chats; GroupMemBench/EverMemBench do not evaluate segment-level units. MemGPT-style paging is shown to degrade reasoning in a group setting only on GroupMemBench (retrieves adequately but answers worse) and the cause is not isolated.
- **Minimal offline test (write as pytest, no model):** build a synthetic fixture of ~200 messages from 5 speakers across 3 interleaved threads, each with one gold message id per question. Index three variants in Postgres: (1) per-message tsvector, (2) per-message + appended extracted fact string (hand-written fixture facts), (3) per-day concatenation. Assert recall@5 of the gold message id is (1) >= (3) and (2) >= (1) on a question set where the question uses wording from a fact paraphrase. This tests the unit-of-memory claim with zero LLM calls.

### Gaps
- No paper compares message-level vs segment-level vs fact-level units on interleaved multi-party chats. EverMemBench retrieval granularity ablation (appendix) not read.

## 2. What retrieval works (BM25, dense, hybrid, rerank, graph expansion, recency/importance)?

### Takeaway
In the multi-party and long-conversation benchmarks, BM25 over raw text is a strong, cheap baseline that often beats dense retrieval and most memory systems; dense retrieval wins on LongMemEval and large-embedding document QA. I found no paper in this set that reports a controlled hybrid (BM25 + dense + RRF) ablation on a conversational memory benchmark, so "hybrid is best" is unproven here. Reranking evidence is thin; graph expansion (HippoRAG) is the only graph method that holds up on group chats.

### Cited Findings
- **BM25 beats dense on group-chat data:** GroupMemBench average 43.22 (BM25) vs 38.04 (text-embedding-3-large); breakdown BM25 vs dense: Temporal 54.94 vs 32.72, Knowledge update 25.23 vs 23.36, Multi-hop 40.11 vs 36.26; dense wins on Term ambiguity (21.70 vs 14.15) and User-implicit (46.94 vs 40.82). — [2605.14498 Table 2](https://arxiv.org/abs/2605.14498)
- **Same direction on EverMemBench/GroupMemBench in the follow-up paper:** BM25 is "the strongest comparison" on EverMem open-ended (27.0 vs dense 23.9) and EM-All 52.5 vs 45.9 (DeepSeek-V4-Flash block); with GPT-5.6-luna block EM-All BM25 56.3 vs Embed 47.8. On SocialMemBench, dense beats BM25 (38.1 vs 28.6; 36.4 vs 30.0). — [2609.26780 Table 1](https://arxiv.org/abs/2609.26780)
- **Dense wins on dyadic LongMemEval:** Table 9, Recall@5 with value=session, K=V: BM25 0.634, Contriever 0.723, Stella V5 1.5B 0.720; value=round: BM25 0.472, Contriever 0.589, Stella 0.660. Authors: "Both dense retrieval embeddings have significantly higher performance than the BM25 sparse retrieval method. The trend is the same across most settings." — [2410.10813 Appendix E.2, Table 9](https://arxiv.org/abs/2410.10813)
- **Mixed on MemoryAgentBench:** BM25 beats dense on accurate-retrieval average (60.5 vs 54.6 for text-embedding-3-large, 54.7 for Qwen3-Embedding-4B, 33.9 Contriever); on LongMemEval subset LME(S*) dense is better (BM25 45.3 vs text-embed-3-large 50.3). — [2507.05257 Table 3](https://arxiv.org/abs/2507.05257)
- **SeCom, LoCoMo:** BM25 beat MPNet at turn level (65.58 vs 57.99) and session level (63.16 vs 51.18); on Long-MT-Bench+ turn-level MPNet beat BM25 (84.91 vs 82.85). — [2502.05589 Table 1](https://arxiv.org/abs/2502.05589)
- **Document QA (not conversational), HippoRAG 2 Table 3 passage recall@5:** BM25 average 55.1, Contriever 55.4, GTR 60.7, NV-Embed-v2 (7B) 73.4, HippoRAG 2 78.2. QA F1 average (Table 2): BM25 47.7, NV-Embed-v2 57.0, HippoRAG 2 59.8. BM25 beats Contriever on 2Wiki QA F1 (51.2 vs 41.9). — [2502.14802 Tables 2-3](https://arxiv.org/abs/2502.14802)
- **Hybrid:** Zep describes three first-stage search functions (cosine, Okapi BM25 via Lucene, breadth-first graph search) and rerankers (RRF, MMR, episode-mentions, node-distance) but reports no ablation of them in its evaluation. — [2501.13956 Sec 3.1-3.2](https://arxiv.org/abs/2501.13956) (vendor). A keyword search of the Mem0, A-Mem, LongMemEval, GroupMemBench, EverMemBench, SpeakerMem-R1 texts found no hybrid-retrieval experiment.
- **Reranking:** RMM's learned reranker (retrospective reflection), Table 2 ablation, Contriever + Gemini-1.5-Flash: RAG 24.8 METEOR / 54.3 R@5 / 58.8 acc; + prospective reflection 28.6 / 57.4 / 59.6; retrospective reflection without a reranker (retriever fine-tuned instead) 20.3 / 34.2 / 31.0 (worse than RAG); + RR with reranker 27.5 / 58.8 / 60.2; full RMM 30.8 / 60.4 / 61.2. Table 1 (GTE retriever): RAG 62.4 R@5 / 63.6 acc, RMM 69.8 / 70.4, oracle 100 / 90.2 on LongMemEval. — [2503.08026 Tables 1-2](https://arxiv.org/abs/2503.08026)
- **Time-aware filtering (LongMemEval Table 4, temporal subset, value=round, K=V+fact):** Recall@10 0.550 without; 0.722 with GPT-4o-extracted time range; 0.570 with Llama-3.1-8B extracting the range. Authors: gain "depends on using a strong LLM". — [2410.10813 Sec 5.4, Table 4](https://arxiv.org/abs/2410.10813)
- **Recency/importance/relevance (Generative Agents):** score = alpha_recency*recency + alpha_importance*importance + alpha_relevance*relevance with all alphas = 1 and each min-max scaled to [0,1]; recency is exponential decay with factor 0.995 per sandbox hour since last retrieval; importance is an LLM-assigned integer 1-10 at write time; relevance is embedding cosine. Ablation (TrueSkill, human rankings of believability, 100 rank sets): full 29.89 (sigma 0.72), no reflection 26.88, no reflection or planning 25.64, human crowdworkers 22.95, no memory/planning/reflection 21.21. — [2304.03442 Sec 4.1, 6.4-6.5](https://arxiv.org/abs/2304.03442)
- **Graph expansion in group chats:** HippoRAG (entity graph + Personalized PageRank over raw passages) is the best non-reflective system: GroupMemBench average 39.72, EverMem MC 62.9 vs BM25 64.4, "HippoRAG sits on the cost-accuracy Pareto front in all four domains"; GraphRAG (summarised communities) scores 20.56 average, "costs more and trails by 14-25 absolute accuracy points". — [2605.14498 Sec 4.3](https://arxiv.org/abs/2605.14498)
- **top-k:** A-Mem finds F1 plateaus or slightly drops past k = 30-40 (Fig 3, GPT-4o-mini, e.g. adversarial 50.03 at k=40 vs 47.76 at k=50; multi-hop 27.02 at k=40, 26.81 at k=50). LoCoMo: observation retrieval peaks at top-5 and declines (41.4 -> 37.8 at top-50). EverMemBench memory systems used top-k 10 (Zep, Mem0) or 20 (MemOS) and feed roughly 1K-3K tokens per query. — [2502.12110 Fig 3](https://arxiv.org/abs/2502.12110); [2402.17753 Table 3](https://arxiv.org/abs/2402.17753); [2602.01313 Sec 4.1](https://arxiv.org/abs/2602.01313)
- **Failure is retrieval, not reasoning, in group chats:** across baselines, retrieval failures are 41-79% of questions and reasoning failures 7-24%; "given the gold message, current LLMs reliably synthesise a correct answer". EverMemBench oracle evidence lifts GPT-4.1-mini multi-hop from 2.41% to 97.99% and Gemini-3-Flash from 26.51% to 88.37% (Table 5). — [2605.14498 Sec 4.4, Fig 5](https://arxiv.org/abs/2605.14498); [2602.01313 Tables 4-5](https://arxiv.org/abs/2602.01313)
- **Full context still beats retrieval for strong models:** EverMemBench average, Gemini-3-Flash full context 72.61 vs +MemOS 59.27, +Zep 54.90, +Mem0 52.12, +MemoBase 55.83 (-13 to -20 points); for GPT-4.1-mini full context 37.44 vs +MemOS 42.55, +Zep 39.97, +Mem0 37.09, +MemoBase 34.27. — [2602.01313 Table 4](https://arxiv.org/abs/2602.01313)

### Inferences
- **What we should copy:** lexical retrieval over raw text as the always-on first stage (we already have Postgres full-text), with dense as a second path; the cost of adding BM25 is effectively zero (GroupMemBench: "effectively $0" ingestion). Add speaker, thread and time as hard filters or boosters, not as text. Treat top-k as a small number (5-10 messages / segments) and measure whether more helps.
- **What the numbers do not show:** (1) hybrid fusion is not measured anywhere I read, so the claim "BM25 + dense + RRF > either" is an inference from ensemble logic, not evidence. (2) BM25-wins results come from synthetic corpora generated by LLMs from templates (GroupMemBench is GPT-5-generated; EverMemBench is blueprint-constrained LLM generation), where role vocabulary is engineered; the BM25 lead may shrink on real chat noise. (3) GroupMemBench filters queries that a retrieval baseline failed on, which could bias which retriever looks good (which baseline unconfirmed). (4) BM25 is weak on term ambiguity (14.15) and on questions phrased in a different role's vocabulary, exactly the case dense or query expansion should help. (5) Generative Agents' weighting was validated for believability of simulated agents, not for factual QA; the equal alphas were not tuned in the paper.
- **Minimal offline test:** generate a fixture of messages where the same fact is stated in two vocabularies (engineer says "PPO run lands Friday", manager asks "alignment status?") plus distractors. Compute recall@5 of the gold message for (a) Postgres FTS, (b) a deterministic fake embedding (plumbing check only) and (c) RRF of both. In CI only assert plumbing and that the lexical path finds same-vocabulary items; keep a nightly, non-CI job with a real embedding model to measure the vocabulary-shift case. Add a recency/importance unit test that checks the Generative-Agents score with fixed vectors and fixed timestamps (pure arithmetic).

### Gaps
- No controlled hybrid or reranker comparison on conversational benchmarks found. Zep's per-component ablation is absent. Hindsight's retrieval design (best on GroupMemBench) not read.

## 3. What consolidation works and what hurts (summaries losing facts)?

### Takeaway
Consolidation that replaces source text loses facts and speaker context; consolidation that adds an index layer on top of kept source text helps. Overwrite-style consolidation fails on knowledge updates in multi-user settings. Reflection-style synthesis helps believability and some QA but is not shown to help group attribution.

### Cited Findings
- Summary loss in LoCoMo: session-summary RAG F1 29.9-32.5 vs dialog-turn RAG 34.6-35.8 even at 90.7% summary recall (see Section 1). Event-summarisation task: best FactScore F1 is 45.9 (gpt-3.5-turbo, 4k) and long-context gpt-3.5-turbo-16k 39.9 (Table 4); error taxonomy in Table 7 lists five error types. — [2402.17753 Tables 3-4, 7](https://arxiv.org/abs/2402.17753)
- LongMemEval: ChatGPT memory "tended to overwrite crucial information as the chat continues, while Coze often failed to record indirectly provided user information"; accuracy with GPT-4o: offline reading 0.9184, ChatGPT 0.5773, Coze 0.3299 (Fig 3a; online runs used 97 questions with 3-6 session histories). — [2410.10813 Sec 3.4](https://arxiv.org/abs/2410.10813)
- Mem0 on GroupMemBench knowledge update: 4.67% (best system 27.1%), and the authors attribute it to the extractor appending "new statements alongside obsolete ones without speaker-conditioned consolidation" (authors' explanation, no ablation). Hindsight's note aggregation raised Multi-hop (42.31) and Ambiguity (37.74) "the same aggregation that locks old decisions and drives its Update score below 18%" (17.76). — [2605.14498 Table 2, Sec 4.2](https://arxiv.org/abs/2605.14498)
- GroupMemBench: MemGPT "retrieving adequately yet answering far worse, the signature of a representation that degrades downstream reasoning"; and "BM25, which feeds the LLM raw message text, attains the highest mean conditional accuracy [P(correct | gold retrieved)] in both domains". — [2605.14498 Sec 4.4](https://arxiv.org/abs/2605.14498)
- MemoryAgentBench selective forgetting (FactConsolidation, conflicting facts over time): multi-hop accuracy at most 28% for any agent in Table 3 (GPT-5-mini long-context 28.0; BM25 3.0; Mem0 2.0; Zep 3.0); single-hop: GPT-5-mini long-context 78.0, GPT-4o 60.0, BM25 48.0, HippoRAG-v2 54.0, Mem0 18.0, Zep 7.0, MemGPT 28.0. Reasoning-model check (Table 5): o4-mini FC-SH 100.0 (6K context) -> 61.0 (32K); FC-MH 80.0 -> 14.0. — [2507.05257 Tables 3, 5](https://arxiv.org/abs/2507.05257)
- Long-range understanding (summarisation, detective QA): long-context models win; RAG and commercial memory "retrieve only partial information ... lacking the ability to capture a holistic understanding" (e.g. Summ. avg: Claude-3.7-Sonnet 52.5 vs BM25 19.0, Mem0 4.8, Zep 4.2, MemGPT 2.5). — [2507.05257 Table 3, Sec 4.2](https://arxiv.org/abs/2507.05257)
- Reflection helps: Generative Agents' reflection ablation (no-reflection 26.88 vs full 29.89 TrueSkill); reflection is triggered when summed importance of recent events exceeds 150, "roughly two or three times a day"; reflections are stored as ordinary memories and retrieved alongside observations. — [2304.03442 Sec 4.2, 6.5](https://arxiv.org/abs/2304.03442)
- A-Mem ablation (GPT-4o-mini, F1): without link generation and memory evolution 9.65 multi-hop / 24.55 temporal / 13.28 single-hop; without evolution 21.35 / 31.24 / 39.17; full 27.02 / 45.85 / 44.65. — [2502.12110 Table 3](https://arxiv.org/abs/2502.12110)
- RMM prospective reflection (topic-organised summaries across utterance/turn/session granularity) adds +3.8 METEOR and +3.1 R@5 on MSC/LongMemEval over plain RAG (Table 2, Contriever). — [2503.08026 Table 2](https://arxiv.org/abs/2503.08026)
- Recursive summaries: MemGPT paper's own baseline (recursive summary) got 35.3% on DMR (Table 2); SeCom ablation numbers RecurSum 56.25/62.96 vs SeCom 69.33 / 88.81. — [2310.08560](https://arxiv.org/abs/2310.08560); [2502.05589 Table 1](https://arxiv.org/abs/2502.05589)
- Style/profile questions (EverMemBench Profile Understanding): memory systems get 11-58% on Style; "communication style is an emergent pattern spanning many interactions; it cannot be recovered from isolated snippets"; Gemini-3-Flash full context 67.05. Profile questions are multiple-choice. — [2602.01313 Sec 4.4](https://arxiv.org/abs/2602.01313)

### Inferences
- **What we should copy:** keep source messages immutable; write consolidated state as separate, versioned rows with `supersedes` / `valid_from` / `valid_to` and a speaker owner; never overwrite a fact attributed to one person because another person said something conflicting (GroupMemBench knowledge-update category is exactly "incompatible preferences across users"); refresh derived notes periodically rather than per message.
- **What the numbers do not show:** none of the consolidation methods are evaluated on whether a *wrong* fact was written (no write-side precision metric); SpeakerMem-R1 is the only paper that trains/measures write quality (SpeakerLevenshtein reward; 305-question controlled test: SFT writer 57.38%, RL writer 68.20%, large-LLM writer 71.48%, Table 3) and it is a single, not-replicated study. Consolidation cost is not weighed against accuracy in the dyadic papers; GroupMemBench shows cost buys 2-12 points at most.
- **Minimal offline test:** a "supersede" test with FakeLLM-free fixtures: write fact(speaker A, "deadline = Nov 5", t1); write fact(speaker B, "deadline = Nov 12", t2) and fact(speaker A, "deadline = Nov 12", t3). Assert: current-state query returns Nov 12 with provenance ids; history query returns all three; speaker B's earlier belief remains addressable as B's; and deleting the source message deletes derived rows. Pure DB logic.

### Gaps
- No paper isolates write-side error rate (hallucinated or mis-attributed facts) for Mem0/Zep/A-Mem. Hindsight reflection stage not read.

## 4. Speaker attribution, temporal reasoning, knowledge updates, abstention

### Takeaway
Attribution and knowledge update are where current systems collapse in group settings; temporal reasoning is easy when dates are pinned and hard when decisions are revised (version semantics); abstention is generally good, but sometimes only because the memory is conservative.

### Cited Findings
**Speaker attribution**
- GroupMemBench defines speaker-grounded belief tracking and binds every question to the asker; on "User-implicit" (first-person questions) "the best agent memory system matches a bare text-embedding-3-large retriever, indicating no real per-user modeling" (best agent systems: A-Mem 46.94 vs text-embedding-3-large 46.94). The authors note that existing systems use `user_id` "as an isolated namespace that separates data stores rather than as a semantic attribute that conditions extraction and retrieval". — [2605.14498 Sec 2, 4.2](https://arxiv.org/abs/2605.14498)
- SpeakerMem-R1 GroupMemBench per-category (Table 16, DeepSeek-V4-Flash): User-implicit 51.0 vs BM25 46.9, Mem0 10.2, A-Mem 22.4; Term ambiguity 31.1 (no-ASK variant 36.8) vs BM25 15.1, A-Mem 25.5; Knowledge update 33.6 vs BM25 23.4. — [2609.26780 Table 16](https://arxiv.org/abs/2609.26780)
- Two-party attribution failure by the benchmarker: the Zep authors state Mem0's LoCoMo run of Zep "utilized a user graph structure designed for single user-assistant interactions but assigned the user role to both participants" and passed timestamps as message text rather than the dedicated field (vendor claim, unverified by a third party). — [Zep blog](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)
- Zep's graph-extraction prompt hardcodes speakers as nodes: "ALWAYS extract the speaker/actor as the first node. The speaker is the part before the colon in each line of dialogue." — [2501.13956 Appendix 6.1.1](https://arxiv.org/abs/2501.13956) (vendor)
- LoCoMo's own observation format stores "assertions about each speaker" (per-speaker observations), and observation retrieval is the best RAG variant at top-5 (41.4 F1 vs 31.7 for raw dialog). — [2402.17753 Sec 3.3, Table 3](https://arxiv.org/abs/2402.17753)
- LoCoMo data issue: the Zep authors report "Some questions incorrectly attribute actions or statements to the wrong speaker" in LoCoMo (vendor claim). — [Zep blog](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)

**Temporal reasoning**
- LoCoMo: temporal is among the hardest categories; GPT-3.5-turbo-16k temporal F1 16.8-25.0 vs human 92.6 (Table 2); observation retrieval raises temporal F1 from 21.3 (dialog top-5) to 41.9. — [2402.17753 Tables 2-3](https://arxiv.org/abs/2402.17753)
- Mem0 paper (vendor): temporal J: Mem0 55.51, Mem0g (graph) 58.13, Zep 49.31, OpenAI memory 21.71, LangMem 23.43; authors say OpenAI memory "underperforms, with scores below 15%, primarily due to missing timestamps in most generated memories despite explicit prompting". — [2504.19413 Table 1, Sec 4.1](https://arxiv.org/abs/2504.19413)
- Zep (vendor) LongMemEval-s temporal-reasoning: gpt-4o full context 45.1% vs Zep 62.4%; gpt-4o-mini 36.5% vs 54.1%. Zep uses bi-temporal edges with valid_at/invalid_at and resolves relative dates against the message reference timestamp. — [2501.13956 Table 3, Sec 2](https://arxiv.org/abs/2501.13956)
- EverMemBench temporal (open-ended): GPT-4.1-mini full context 7.00, Gemini-3-Flash 45.00, memory systems 2.67-21.00; even with oracle evidence 60.00 / 54.33 / 34.00 (GPT-4.1-mini / Gemini / Llama-4-Scout, Table 5), because evidence contains "premature completion announcements and archival statements from other speakers on adjacent dates"; "they treat time as an ordering signal rather than a semantic construct that encodes event lifecycle stages". — [2602.01313 Sec 4.2, Tables 4-5](https://arxiv.org/abs/2602.01313)
- GroupMemBench temporal: BM25 54.94, Hindsight 54.94, embedding 32.72, Mem0 16.67; conditional on retrieving the gold message temporal is "uniformly high, effectively solved" (Fig 6). Questions are pinned to dates/relative expressions. — [2605.14498 Table 2, Sec 4.4](https://arxiv.org/abs/2605.14498)
- LongMemEval temporal-aware indexing: see Section 2 (Recall@10 0.550 -> 0.722 with GPT-4o time-range extraction).

**Knowledge update**
- GroupMemBench: no system passes 28% (best 27.10 HippoRAG; BM25 25.23; Mem0 4.67; Hindsight 17.76). — [2605.14498 Table 2](https://arxiv.org/abs/2605.14498)
- LongMemEval/Zep (vendor) knowledge-update: gpt-4o full context 78.2% vs Zep 83.3%; gpt-4o-mini 76.9% vs 74.4%. — [2501.13956 Table 3](https://arxiv.org/abs/2501.13956)
- EverMemBench "Updating" (multiple-choice): GPT-4.1-mini full context 42.54, +Zep 43.66, +Mem0 51.87, +MemOS 45.15; Gemini-3-Flash full context 100.0, memory systems 78.36-90.67; oracle 98.51 / 99.23. — [2602.01313 Tables 4-5](https://arxiv.org/abs/2602.01313)
- MemoryAgentBench FactConsolidation: see Section 3.

**Abstention**
- LoCoMo adversarial: gpt-3.5-turbo-16k F1 falls from 13.1 (4K context) to 2.1 (16K) while gpt-4-turbo at 4K gets 70.2 (Table 2); "LLMs can be easily misled into generating hallucinations when they are subjected to long contexts"; observation-RAG top-5 gets 44.7. — [2402.17753 Table 2-3, Sec 6.1](https://arxiv.org/abs/2402.17753)
- GroupMemBench abstention: 67.89 (A-Mem) to 82.57 (Mem0); "Mem0's high Abstention is conservative storage rather than calibrated refusal". SpeakerMem-R1 table 16: abstention BM25 89.9 vs SpeakerMem-R1 73.4/71.2 (different answerer/judge than Table 2; not comparable in absolute terms). — [2605.14498 Sec 4.2](https://arxiv.org/abs/2605.14498); [2609.26780 Table 16](https://arxiv.org/abs/2609.26780)
- LongMemEval abstention: 30 false-premise questions derived from other types; judge GPT-4o agreement with human experts above 97%. — [2410.10813 Sec 3.2-3.3](https://arxiv.org/abs/2410.10813)

### Inferences
- **What we should copy:** (1) make speaker id a first-class retrieval filter and a first-class field in every derived fact; (2) resolve relative dates at write time using the message timestamp (Zep, LongMemEval time-aware indexing); (3) represent decisions as versioned state with lifecycle (proposed / decided / superseded / completed) because EverMemBench shows oracle evidence still gives only 34-60% on temporal when lifecycle is ambiguous; (4) abstain on a retrieval-score floor in code, not just by prompt, and measure refusal calibration (do not copy "high abstention" as a success, since conservative storage inflates it).
- **What the numbers do not show:** EverMemBench Memory Awareness/Profile are multiple-choice (non-zero chance level) while Fine-Grained Recall is open-ended with an LLM judge, so averages across sub-tasks mix formats; the "Gemini full context 100% on Update" figure shows the question is answerable when the model sees everything, and says little about retrieval-based architectures. GroupMemBench's temporal result ("solved given retrieval") and EverMemBench's ("unsolved even with oracle") conflict, probably because of question design (date-pinned vs lifecycle/duration arithmetic) but no paper tests that explanation.
- **Minimal offline test:** (a) deterministic date test: message "ship by EOD Friday" at timestamp 2026-03-04T10:00Z must be stored with absolute date 2026-03-06 (pure function, no LLM); (b) speaker-binding test: two speakers state different preferences for the same slot ("I prefer Postgres" / "I prefer SQLite"); query "my preference" from each speaker returns only that speaker's row; (c) abstention test: a question about an entity absent from the store must return an empty retrieval set under the score floor and a fixed refusal from the policy layer.

### Gaps
- No paper measures speaker-attribution error rate directly (who said what) in retrieved context. SocialMemBench (norms/relations) not read.

## 5. What fails in multi-party settings, and what mitigations are demonstrated

### Takeaway
Reported failures are: attribution across speakers and groups, topic interleaving across threads, information asymmetry/role vocabulary (term ambiguity), and knowledge updates through back-and-forth. Demonstrated mitigations: keep verbatim speaker-labelled text, add per-person and per-group derived views with provenance, retrieve per participant/event/time, and feed oracle-quality evidence. Demonstrated gains are modest (3-13 points) and come from a single follow-up paper.

### Cited Findings
- Multi-group degradation (EverMemBench Fig 4 text): accuracy drops "from 54.5% (single-group) to 33.6% (two groups) and 19.7% (three groups), a 64% relative decline ... cross-group attribution - not context length - is the dominant challenge". The figure itself labels the overall average 53.2 / 33.2 / 17.6 (the text and figure aggregates differ slightly; I could not reconcile). — [2602.01313 Sec 4.2, Fig 4](https://arxiv.org/abs/2602.01313)
- Multi-hop collapse under multi-party: Gemini-3-Flash full context 26.51%, best memory-augmented system 18.88% (GPT-4.1-mini + MemOS); with oracle spans GPT-4.1-mini 97.99%, Gemini 88.37%, Llama-4-Scout 37.35% (Llama "frequently refus[es] to answer when evidence appears fragmented"). Single-hop is largely fine (Gemini 97.65; memory systems 55-83). — [2602.01313 Tables 4-5, Sec 4.2](https://arxiv.org/abs/2602.01313)
- Dataset stats (EverMemBench): 5 projects, 170 employees, 51,023 turns, 4.2M tokens (about 1M per project), 2,400 QA; 37.6 personas per batch vs 2 for LoCoMo (Table 1, Table 3). GroupMemBench: 123 topics, 120K turns, 2.7M tokens avg dialogue (Table 1), 745 questions (per [2609.26780](https://arxiv.org/abs/2609.26780)); reply structure is controllable with mixture weights 0.2 post / 0.6 threaded reply / 0.2 cross-project (Sec 3.2); realism perturbations: ~5% noise messages, ~25% disagreement turns, ~20% stylistic imperfections, ~5% decision changes. — [2602.01313 Sec 3.4](https://arxiv.org/abs/2602.01313); [2605.14498 Sec 3.2](https://arxiv.org/abs/2605.14498)
- Term ambiguity / audience-adapted language (GroupMemBench): "token" can mean text unit or credential; engineer's "PPO" vs manager's "alignment". Term-ambiguity accuracy stays below 38% for all baselines (Hindsight 37.74, HippoRAG 30.19, A-Mem 26.42, text-emb-3-large 21.70, BM25 14.15) and P(correct | gold retrieved) stays below 40% across nearly every cell, "the only type where representation, not retrieval, is the wall". — [2605.14498 Sec 4.2, 4.4](https://arxiv.org/abs/2605.14498)
- Ingest cost and accuracy trade-off (GroupMemBench Sec 4.3): per-domain ingestion cost $0.31-$51.04, storage 0.69-8.63 GB; HippoRAG on the Pareto front in all four domains; Hindsight best accuracy at "2-5x HippoRAG's cost" for "2-12 absolute accuracy points". — [2605.14498 Sec 4.3](https://arxiv.org/abs/2605.14498)
- SpeakerMem-R1 headline (accuracy %, DeepSeek-V4-Flash block): GroupMem 47.9 (BM25 44.6), SocialMem 69.2 (A-Mem 56.8, full context 69.4), EverMem-All 61.9 (BM25 52.5). With GPT-5.6-luna block: GroupMem 42.7 (BM25 46.2, i.e. below BM25), SocialMem 64.4 (HippoRAG 61.3), EverMem-All 60.0 (HippoRAG 57.6). On the public EverMemBench leaderboard configuration (GPT-4.1-mini answerer, Gemini-3-Flash judge): SpeakerMem-R1 62.33% vs EverOS ~60.08%, RippleMem 54.75%, MemOS 44.63, Zep 41.67, Mem0 39.92, MemoBase 36.21 (the last four match Table 4 of EverMemBench). The authors' own description: "On GroupMem, BM25 ... already reaches 44.6%, while SpeakerMem-R1 obtains 47.9%". — [2609.26780 Tables 1-2, Sec 5.2](https://arxiv.org/abs/2609.26780)
- SpeakerMem-R1 attributes weakness to "message attribution" and "state reconstruction", and claims "Global relevance retrieval does not guarantee that a low-frequency member or the correct branch enters a limited candidate set" (motivation text, not tested separately). It scores 70.85% on all 1,986 LoCoMo questions as a two-person "boundary test" but is below LightRAG (79.87) and MemOS (75.80) on non-adversarial LoCoMo categories using other papers' numbers (Table 4). — [2609.26780 Sec 1, Table 4](https://arxiv.org/abs/2609.26780)
- Multi-party dialogue modelling (response generation, not memory): HeterMPC models utterance and interlocutor nodes in a heterogeneous graph on Ubuntu IRC; BLEU-1 12.61 (BERT-based) vs BERT 10.90; removing interlocutor nodes drops it to 11.80; human-eval score 2.39-2.41 vs BERT 2.19 / BART 2.24 and human 2.81 (Tables 1-2). Shows speaker/addressee structure helps generation, with modest absolute gains. — [2203.08500 Tables 1-2](https://arxiv.org/abs/2203.08500)
- DialSim (multi-party TV-show QA, from the A-Mem paper): F1 A-Mem 3.45, LoCoMo-style baseline 2.55, MemGPT 1.18 (Table 2); absolute values are very low and the DialSim original paper was not read. — [2502.12110 Table 2](https://arxiv.org/abs/2502.12110)
- Surveys: "Memory in the Age of AI Agents" lists "shared memory for multi-agent systems" as a frontier but its full text contains zero mentions of speakers, group chats or multiple users. — [2512.13564](https://arxiv.org/abs/2512.13564)

### Inferences
- **What we should copy:** (1) raw, speaker-labelled messages as the evidence track (the ablation shows removing it costs 15-27 points); (2) a person-view and a group-view derived layer, each row carrying source message ids, owner (who it is about), scope (personal vs shared) and version; (3) query-time decomposition: anchor on asker identity, entities and time window before ranking, which is how the multi-party benchmarks define their question types; (4) report retrieval-gold-recall and conditional accuracy separately, as GroupMemBench Fig 5-6 does.
- **What the numbers do not show:** all three multi-party benchmarks are LLM-synthesised (GPT-5 for GroupMemBench; blueprint + LLM realisation for EverMemBench), so real-Slack/Telegram messiness is not measured; none involve cross-channel identity linking, per-audience privacy filters, or an assistant that is itself a participant with permissions. The SpeakerMem-R1 gain over BM25 is 3.3 points on GroupMemBench in one config and negative in another (42.7 vs 46.2 with GPT-5.6-luna), i.e. within model/judge noise; its larger gains are on SocialMemBench and EverMem open-ended, and EverMemBench's QA are partly multiple-choice. SpeakerMem-R1 costs 7,771-26,992 tokens/question including ingest vs BM25 1,289 (Tables 11-12).
- **Minimal offline test:** a synthetic "interleaved channels" fixture: 3 channels, 4 speakers, 2 topics interleaved within each channel (A/B/A/B), one decision that is reversed by a different speaker in another channel. Assert (i) retrieval for "what did X say about topic A" returns only X's messages in topic A (speaker + topic filter), (ii) for a question requiring two channels the union of per-channel retrieval contains both gold ids (multi-group recall; measure recall@10 as the number of channels grows 1,2,3 to reproduce the EverMemBench degradation shape on our retriever), (iii) a retrieval-failure vs reasoning-failure split computed from gold-in-context so regressions are attributed correctly.

### Gaps
- Information asymmetry (which participants were present for which message; DM vs channel visibility) and general cross-speaker coreference are not measured by any benchmark I read; GroupMemBench user-implicit (first-person reference to the asker) is the only narrow coreference case. This is a load-bearing absence for an audience-scoped design.
- No paper evaluates per-audience filtering, cross-platform identity merging, or privacy leakage inside a conversational memory benchmark (outside this task's scope but absent from the literature I read). MuTual, Ubuntu IRC original, and discourse-parsing-based memory were not read.

## 6. Cost and latency numbers

### Takeaway
Raw-text BM25 retrieval costs about zero to ingest and about 1-2 s end-to-end per query; LLM-extraction memory systems cost orders of magnitude more at ingestion for no accuracy gain in group settings. Graph and agentic memory have the largest ingestion bills. Full-context is accurate but slow and expensive per query.

### Cited Findings
- GroupMemBench Sec 4.3: ingestion cost $0.31-$51.04 per domain, storage 0.69-8.63 GB; BM25 ingestion "effectively $0" (inverted index only); MemGPT cheapest LLM-ingest system (embedding-only) with accuracy capped 22-35%; Hindsight 2-5x HippoRAG cost. Ingestion used gpt-4o-mini. — [2605.14498](https://arxiv.org/abs/2605.14498)
- SpeakerMem-R1 token accounting (EverMemBench 2,400 questions, Table 12): SpeakerMem-R1+ASK uses 2,049 Writer calls, total 18.65M tokens (7,772/question); BM25 3.09M total (1,289/question); Mem0-chunk5 18.9M (7,893/question) from 10,205 ingestion calls; A-Mem 25.9M (10,806); HippoRAG 25.5M (10,612). GroupMemBench (Table 11): SpeakerMem-R1 20.1M tokens (26,992/question); BM25 0.96M (1,289); Mem0 40.6M (54,489); HippoRAG 43.4M (58,232). — [2609.26780 Tables 11-12](https://arxiv.org/abs/2609.26780)
- MemoryAgentBench latency (seconds, Table 12): BM25 memory construction 0.12 s (MH-QA, chunk 512), query 0.47 s; text-embed-3-large 6.1 s / 0.46 s; HippoRAG-v2 1,089 s / 0.71 s; Mem0 10,804 s construction (1,334 s at chunk 4096) with 0.79 s query; Cognee 11,890 s / 58.7 s; MIRIX ~29,000 s (estimated) construction; MemGPT 433 s / 9.4 s. Long-context query latency: GPT-4o-mini 4.9 s, GPT-4o 17.0 s, Claude-3.7-Sonnet 23.3 s on MH-QA (Table 11). Per-query cost (Table 17): BM25 <$0.001-$0.006; GPT-4.1-mini long-context $0.043 on MH-Doc QA; MIRIX (GPT-4.1-mini) $0.016. — [2507.05257 Tables 11-12, 17](https://arxiv.org/abs/2507.05257)
- Mem0 (vendor) LoCoMo latency (Table 2; seconds p50/p95): Mem0 search 0.148/0.200, total 0.708/1.440, 1,764 memory tokens, overall J 66.88; Mem0g total 1.091/2.590, 3,616 tokens, J 68.44; Zep search 0.513/0.778, total 1.292/2.926, 3,911 tokens, J 65.99; A-Mem 2,520 tokens, total 1.410/4.374, J 48.38; LangMem search p50 17.99 s / p95 59.82 s, J 58.10; full-context 26,031 tokens, total 9.870/17.117 s, J 72.90; best RAG chunk setting 256 tokens k=2: J 60.97 (8192 k=2: 60.53, total p95 9.942 s). Authors: Mem0 p95 latency 92% lower than full-context at 66.88 vs 72.90 J. — [2504.19413 Table 2, Sec 4.3-4.4](https://arxiv.org/abs/2504.19413) (vendor-reported)
- Zep (vendor) LongMemEval-s: full-context gpt-4o-mini 55.4% at 31.3 s / 115k tokens vs Zep 63.8% at 3.20 s / 1.6k tokens; gpt-4o 60.2% at 28.9 s vs Zep 71.2% at 2.58 s. Zep tested over the network from a residential laptop to AWS us-west-2. — [2501.13956 Table 2](https://arxiv.org/abs/2501.13956)
- A-Mem: retrieval time at 1M entries 3.70 microseconds vs MemoryBank 1.91 and ReadAgent 120,069.68 microseconds; per-entry storage O(N) (1,464.84 MB at 1M). LoCoMo prompt tokens: 2,520 (A-Mem, GPT-4o-mini) and 1,216 (GPT-4o) vs 16,910 for the LoCoMo baseline. These timings are for the vector search step only. — [2502.12110 Table 1, 4](https://arxiv.org/abs/2502.12110)
- HippoRAG 2 on 11,656 MuSiQue passages (Table 12): 9.2M input + 3.0M output tokens for indexing, 99.5 min indexing, 1.2 s QA/query, 9.9 GB GPU; GraphRAG 115.5M input (1,255% of HippoRAG 2), 277 min, 10.7 s/query; LightRAG 68.5M input, 13.3 s/query; NV-Embed-v2 12.1 min, 0.3 s/query. — [2502.14802 Table 12](https://arxiv.org/abs/2502.14802)
- MemoryOS: 3,874 recalled tokens and 4.9 LLM calls per response (vs A-Mem* 13.0, MemGPT 4.3 calls/16,977 tokens). — [2506.06326 Table 3](https://arxiv.org/abs/2506.06326)
- EverMemBench: memory systems consume "roughly 1K-3K input tokens per query, whereas full-context baselines ingest the entire ~1M-token dialogue history". — [2602.01313 Sec 4.1](https://arxiv.org/abs/2602.01313)
- LongMemEval: pilot shows 30-60% accuracy decline for long-context readers on 115k-token histories (GPT-4o 0.870 oracle -> 0.606 on S, 30.3% drop; Llama-3.1-70B 0.744 -> 0.334); optimal retrieved-token budget varies by reader (Llama-3.1-8B drops sharply beyond 3k retrieved tokens; GPT-4o keeps improving beyond 20k). — [2410.10813 Fig 3b, Sec 5.2](https://arxiv.org/abs/2410.10813)

### Inferences
- **What we should copy:** make the always-on path cheap (FTS + dense on raw messages, no LLM at ingest), and run LLM extraction only in a background job so write-path latency and the spend cap are not driven by memory; budget top-k tokens per reader model (small reader: about 3k tokens).
- **What the numbers do not show:** vendor latency numbers (Mem0, Zep) are from different networks, concurrency settings and hardware; Zep's blog says Mem0 ran sequential searches. The per-question token tables in SpeakerMem-R1 hold query top-k fixed so "1,289 tokens" for BM25 is a design constant, not a measurement of an optimal budget. Dollar costs in GroupMemBench use gpt-4o-mini prices at the time and the Table 11 values were not read.
- **Minimal offline test:** a test that counts model calls: ingesting 1,000 fixture messages through the always-on path must make 0 LLM calls (assert FakeLLM call_count == 0) and the background consolidator must call the fake at most one call per N messages; plus a latency budget test for the SQL retrieval query on a 100k-row fixture (asserting an index is used via EXPLAIN).

### Gaps
- No independent latency measurement for Hindsight or SpeakerMem-R1 query path. Dollar costs in GroupMemBench Table 11 not read.

## 7. Reliability of the headline numbers (vendor-reported, disputes, critiques)

### Takeaway
LoCoMo leaderboard numbers across vendors are not comparable: category labels, which categories are included, judge model, and implementation correctness differ, and the vendors dispute each other. Full-context baselines beat the memory systems in the vendors' own tables on LoCoMo.

### Cited Findings
- Mem0 paper (vendor) Table 2: Mem0 J=66.88, Mem0g 68.44, Zep 65.99, full-context 72.90, OpenAI memory 52.90, A-Mem 48.38. Zep (vendor rebuttal) says the Zep figure is wrong due to implementation errors, and reports 75.14% +/- 0.17 for correctly implemented Zep after an earlier erroneous higher figure was corrected; Zep paper itself reports no LoCoMo numbers (only DMR and LongMemEval; see [Table 1-3](https://arxiv.org/abs/2501.13956)). The Zep page's note on newer scores ("80% at <200ms") is dated "December 9, 2015" on the page, which is evidently a typo; I could not verify the date or method. — [2504.19413](https://arxiv.org/abs/2504.19413); [Zep blog](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)
- Zep's critique of LoCoMo (vendor): conversations "around 16,000-26,000 tokens"; "Mem0's own results show their system being outperformed by a simple full-context baseline ... ~73%, compared to Mem0's best score of ~68%"; the benchmark "lacks questions designed to test knowledge updates"; Category 5 unusable "due to missing ground truth answers"; multimodal questions reference image details missing from captions; underspecified questions. — [Zep blog](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)
- Category-label inconsistency I verified in the papers' own tables: the same numbers are labelled differently. The "LoCoMo" full-context row with GPT-4o-mini F1 25.02/12.04/40.36/18.41 is labelled Multi Hop / Open Domain / Single Hop / Temporal in A-Mem's Table 1, but Single Hop / Multi-Hop / Open Domain / Temporal in Mem0's Table 1; MemoryOS lists A-Mem's 27.02 under "Single Hop" while A-Mem lists it under "Multi Hop". The original LoCoMo paper's Table 2 uses its own order (Single Hop, Multi Hop, Temporal, Open Domain, Adversarial). Comparing per-category numbers across these papers is unsafe. — [2502.12110 Table 1](https://arxiv.org/abs/2502.12110); [2504.19413 Table 1](https://arxiv.org/abs/2504.19413); [2506.06326 Table 2](https://arxiv.org/abs/2506.06326); [2402.17753 Table 2](https://arxiv.org/abs/2402.17753)
- A-Mem does not uniformly beat the LoCoMo full-context baseline in its own Table 1: with GPT-4o, Single Hop F1 48.43 (A-Mem) vs 61.56 (LoCoMo baseline), Adversarial 36.35 vs 52.61; with GPT-4o-mini Adversarial 50.03 vs 69.23. — [2502.12110 Table 1](https://arxiv.org/abs/2502.12110)
- MemGPT vs full-context: the MemGPT paper's DMR baseline was a lossy recursive summary; replications with simple full-conversation context score as high or higher (94.4-98.0% vs 93.4% for MemGPT) and MemTree measured MemGPT at 70.4 vs full history 95.6 with GPT-4o. Zep also states "We were unable to reproduce MemGPT's results using gpt-4o-mini due to insufficient methodological details" and that DMR questions are "ambiguous" and fit in context. — [2501.13956 Sec 4.2](https://arxiv.org/abs/2501.13956); [2410.14052 Table 1](https://arxiv.org/abs/2410.14052)
- Single-author critique (low weight): ATANT v1.1 claims an "empty-gold scoring bug in the LOCOMO reference implementation that renders 23% of its corpus unscorable", and lists unreproducible-score issues on the Mem0 and Zep GitHub trackers (mem0 issues #2800, #3943, #3944; zep-papers issue #5). Only the abstract and the LoCoMo paragraphs were read; the author sells a competing product; I did not verify the issue pages. — [2604.10981](https://arxiv.org/abs/2604.10981)
- LongMemEval judge: GPT-4o with question-type prompts, "more than 97% agreement with human experts" (Table 6 in appendix). EverMemBench uses LLM-as-judge for open-ended recall and multiple-choice for awareness/profile; GroupMemBench uses GPT-5 judge validated on a human-annotated subset (appendix I, not read). — [2410.10813 Sec 3.3](https://arxiv.org/abs/2410.10813); [2602.01313 Sec 4.1](https://arxiv.org/abs/2602.01313); [2605.14498 Sec 4.1](https://arxiv.org/abs/2605.14498)
- GroupMemBench abstract states "the strongest one reaches only 46.0% average accuracy, with knowledge update at 27.1% and term ambiguity at 37.7%". In Table 2 those two numbers are best-in-column values from different systems (HippoRAG update 27.10; Hindsight ambiguity 37.74). Hindsight's own update score is 17.76. Read the table, not the abstract. — [2605.14498 abstract and Table 2](https://arxiv.org/abs/2605.14498)

### Inferences
- **What we should copy:** adopt the evaluation hygiene shown here: separate retrieval recall from answer accuracy; always include a full-context and a BM25 baseline; report per-category numbers; pin judge model; and do not rely on LoCoMo category numbers across papers.
- **What the numbers do not show:** none of the vendors' numbers have been independently reproduced in the papers I read except SpeakerMem-R1's and GroupMemBench's own re-runs, where Mem0 and A-Mem are far below their vendor-reported LoCoMo figures (e.g. Mem0 on GroupMemBench 25.73 avg; on EverMem open-ended 1.7). Differences could be caused by configuration (chunk5 ingestion, answerer model, group data vs dyadic) rather than system quality; no paper separates these.
- **Minimal offline test:** build our own tiny regression benchmark in the repo (fixture JSONL: messages, questions, gold message ids, category) and a script that always reports (a) gold recall@k, (b) answer accuracy with a scripted oracle reader, (c) BM25-only baseline accuracy; fail CI if the production retriever's recall@5 falls below the BM25 baseline's on the fixture.

### Gaps
- Later vendor LoCoMo numbers seen in a search-result summary only, not fetched, unverified: Mem0 2026 figure 92.5 (new grading prompt) and Zep 94.7 (gpt-5.4 as answerer and grader), per a third-party page summarised at [braindetox.kr](https://braindetox.kr/en/posts/memory_benchmark_scores_reliability_2026.html) and the ATANT snippet.
- Could not verify the Dev.to / blog claims about LoCoMo answer-key errors (title seen in search results only: "We audited LoCoMo: 64% of the answer key is wrong ..."); not fetched. Could not verify later 2026 vendor LoCoMo numbers.

## 8. Summary table for report writer: what to copy and the minimal offline tests

### Takeaway
Nine design decisions, each tied to the evidence strength above and one offline test.

### Cited Findings
- See Sections 1-7 for sources; the table below only restates them.

### Inferences

| # | Design decision (supported by) | Strength of evidence | Offline test (no model or FakeLLM) |
|---|---|---|---|
| 1 | Keep verbatim speaker-labelled messages as the primary record (GroupMemBench Table 2; SpeakerMem-R1 Fig 4; MemoryAgentBench Table 3; LoCoMo Table 3) | Strong: four independent benchmarks, three groups | gold-message recall@5 on interleaved-thread fixture; ingestion makes 0 LLM calls |
| 2 | Add extracted facts as extra index text appended to the raw key, not a replacement (LongMemEval Table 3, Table 10) | Moderate: one benchmark (dyadic), one retriever family | recall@5 with vs without appended fact strings on paraphrase questions |
| 3 | BM25 + speaker/time filters as default; dense as an additional path (GroupMemBench; MemoryAgentBench vs LongMemEval Table 9) | Mixed: BM25 wins on group chat, dense wins on LongMemEval; hybrid untested | recall@5 for FTS, fake-embedding plumbing, and RRF on a two-vocabulary fixture |
| 4 | Versioned, speaker-owned state; never overwrite another speaker's belief (GroupMemBench update <=27.1%; Mem0 4.67; MemoryAgentBench FC-MH <=28) | Strong problem evidence, weak solution evidence (no system solves it) | supersede/history/coexisting-belief DB test |
| 5 | Resolve relative dates at write time; time-range filter at query (LongMemEval Table 4; Zep) | Moderate | pure date-resolution function test |
| 6 | Query-time conditioning on asker identity (GroupMemBench definition; SpeakerMem-R1 user-implicit 51.0 vs 46.9) | Weak-moderate: one follow-up paper | asker-bound retrieval test with two speakers |
| 7 | Report retrieval recall separately from answer accuracy (GroupMemBench Fig 5-6; EverMemBench oracle Table 5) | Strong methodological | gold-in-context vs answer-correct split in test harness |
| 8 | Abstention by retrieval-score floor in code | Weak: only observational (Mem0 abstention is storage-conservatism) | absent-entity query -> empty retrieval -> fixed refusal |
| 9 | Background, capped consolidation; do not use a heavy memory framework on the write path (GroupMemBench cost $0.31-$51.04/domain; MemoryAgentBench Mem0 10,804 s construction) | Strong on cost, none on accuracy benefit | call-count budget test with FakeLLM |

### Gaps
- Same as Sections 1-7; hybrid retrieval, write-side precision, audience asymmetry and real (non-synthetic) group-chat corpora are unmeasured.
