# Everyone dreams now; prove growth and identity

Nobody ships your whole design: as of 21 October 2026 I found no product, open-source project, AGI lab or paper that combines brain-like memory tiers, surprise segmentation, prioritised sleep, forgetting with re-verification, prediction-error learning, prospective memory, metacognitive gating, a per-person theory of mind and competence-gated developmental stages in one agent. The closest shipped stacks each stop short in a different place: **OpenClaw's memory stack** has nightly patch-style dreaming and cue-based "standing intents" but no segmentation, valid-time facts or stages; **EverMind's EverOS + Raven** has the right tiers and topic-shift episodes but ships its reflection and foresight features switched off; **MemTensor's MemOS** learns skills from rewards and corrections and shares memory through private and shared "cubes," but its LoRA tier is still "coming soon." Honcho (person models), Zep/Graphiti (time-valid facts) and Claude Managed Agents (non-destructive dreams) each own one piece, and the nearest research systems (ZenBrain, Sophia's "System 3," The Digital Apprentice, Nemori, MIRIX, LightMem) never evaluate more than three of your mechanisms. Offline "sleep" consolidation became a standard feature in 2026, on by default in OpenClaw and shipped in some form by Anthropic, Devin, ChatGPT, Letta and Honcho, so it no longer sets you apart. What has no public precedent is the wiring between the pieces: autonomy earned on measured learning milestones, a self-stated prediction-error signal, replay prioritised by pending intentions, spaced re-verification, confidence-gated proactivity driven by a person model, private-plus-shared memory with LoRA, verified cross-channel identity, and a benchmark that measures growth over months. On identity, every framework surveyed links a person's channels through an operator-maintained map without checking that the same human controls them, and trusting display names has already produced an OpenClaw CVE and a red-team compromise. The fix is an identity service outside the model that keys people on immutable platform IDs, links a new channel only through a code, approval or sign-in delivered via a channel the person already trusts, keeps links reversible, and filters every memory by the audience it came from before retrieval, because even private per-agent memory still produced 43.5% visibility violations in one multi-user benchmark. Your defensible position is the AI hire whose growth you can measure and whose identity checks you can trust, backed by an open growth benchmark that no vendor publishes.

## Dreaming became table stakes in 2026, but integration did not

The single most important market fact for your design is that nightly consolidation is no longer yours to claim. OpenClaw shipped "dreaming" experimentally in v2026.4.5 and made model-backed "grounded dreaming" the default in 2026.8.1, and its docs now state that "Dreaming is enabled by default" ([CHANGELOG 2026.4.5](https://github.com/openclaw/openclaw/blob/main/CHANGELOG/2026.4.5.md); [CHANGELOG 2026.8.1](https://github.com/openclaw/openclaw/blob/main/CHANGELOG/2026.8.1.md); [OpenClaw docs](https://docs.openclaw.ai/concepts/dreaming)). Anthropic opened dreams for Claude Managed Agents as a research preview in May 2026. A dream reads one memory store plus 1–100 past sessions and writes a new store with "duplicates merged, stale or contradicted entries replaced with the latest value, and new insights surfaced" ([Claude docs](https://platform.claude.com/docs/en/managed-agents/dreams)). Cognition gave Devin Git-backed Markdown memory and periodic dreaming on 5 October under an open, MIT-licensed spec, according to secondary reporting ([ExplainX](https://explainx.ai/blog/cognition-devin-dreaming-memory-agent-memory-repo-open-spec-2026)). ChatGPT began curating memories in the background in June because old memories "often became stale" and "could also contradict one another" ([Thurrott](https://www.thurrott.com/a-i/337052/openai-is-improving-how-chatgpts-memory-works); [PCWorld](https://www.pcworld.com/article/3158111/chatgpt-new-dreaming-feature-makes-it-way-better-at-remembering-you.html)). Letta renamed its sleep-time compute "dreaming" ([letta-code README](https://github.com/letta-ai/letta-code)), and Honcho's experimental dreamer bills itself as "sleep for a memory system" ([Honcho docs](https://honcho.dev/docs/v3/documentation/features/advanced/dreaming)).

Learning from corrections and typed memory are just as common. Claude Code's auto memory exists so that Claude can "learn from your corrections without manual effort" ([Claude Code docs](https://code.claude.com/docs/en/memory.md)). Google's Gemini agent, announced on 8 October, advertises session, semantic, procedural and episodic memory and "onboards itself the way a new hire would" ([Google release](https://www.zawya.com/en/press-release/companies-news/welcome-to-gemini-at-work-2026-introducing-the-gemini-agent-1586898)). **Four memory tiers, learning from corrections and overnight consolidation now describe the typical 2026 agent.** Every one of these products consolidates text, not weights. Turing Post's verdict on ChatGPT's version applies to all of them: it is "not proof that parametric continual learning is solved" ([Turing Post](https://www.turingpost.com/p/continual-learning-llms-ai-models-sleep)).

The real differences lie in what each system consolidates and how it edits memory. OpenClaw's dreaming runs as a managed cron sweep that defaults to 03:00 nightly, and its deep phase ranks candidates by relevance (0.30), frequency (0.24), query diversity (0.15), recency (0.15), recurrence across days (0.10) and conceptual richness (0.06). The model "returns operation decisions, not replacement memory prose." A rewrite may lose at most 25% of prior entries, the previous file is saved first, and a "structural taint gate" drops untrusted candidates ([OpenClaw dreaming docs](https://github.com/openclaw/openclaw/blob/main/docs/concepts/dreaming.md)). Anthropic's dream regenerates the whole store instead. Its docs warn that instructions are "a synthesis pass over the inputs, not an editor applied to the text of the store," though the input store is never modified, so a bad dream can be discarded ([Claude docs](https://platform.claude.com/docs/en/managed-agents/dreams)). Honcho's deduction step "replaces outdated facts by deleting the old conclusion" ([Honcho docs](https://honcho.dev/docs/v3/documentation/features/advanced/dreaming)), the opposite of the invalidate-don't-delete rule your design needs. Among shipped products only MemOS weights consolidation by reward, and **nobody feeds pending goals or intentions into replay priority**.

### Three stacks come closest, and each stops short in a different place

**OpenClaw's memory stack** covers the most of your distinctive items. Dated notes lose search weight with a 30-day half-life, while the core MEMORY.md and USER.md files never decay ([memory-search docs](https://github.com/openclaw/openclaw/blob/main/docs/concepts/memory-search.md)). Its memory-wiki stores claims with status, confidence, evidence and freshness, reports contradictions and stale claims, and keeps person cards with "ask-for" and "avoid-asking-for" fields and a privacy tier ([memory-wiki docs](https://github.com/openclaw/openclaw/blob/main/docs/plugins/memory-wiki.md)). Its standing intents are explicitly "prospective memory": the docs split intentions into time-based (scheduled), event-based and aspirational tiers, and event-based intents such as "When Alice mentions the launch, ask about rollback" default to a 24-hour cooldown, at most three firings and a 90-day expiry. Matching uses keyword rules, with "No model call" ([standing-intents docs](https://github.com/openclaw/openclaw/blob/main/docs/concepts/standing-intents.md)). It lacks event segmentation (memory is organised in daily files), valid-time facts, any prediction-error signal, scheduled re-verification, developmental stages, shared role knowledge and weight consolidation. Its own security page warns that it "is not a hostile multi-tenant security boundary" ([OpenClaw security](https://docs.openclaw.ai/gateway/security)).

**EverMind's EverOS (formerly EverMemOS) with its Raven harness** has the tier structure closest to yours. The January 2026 paper describes an "engram-inspired lifecycle." An LLM boundary detector cuts a sliding window wherever the topic shifts. Each "MemCell" holds an episode, atomic facts and time-bounded "Foresight" items, and cells cluster into scenes that update a profile separating stable traits from temporary states ([arXiv 2601.02163](https://arxiv.org/html/2601.02163v1)). The shipped runtime derives facts, a profile, cases and SKILL.md skills offline ([EverOS docs](https://github.com/EverMind-AI/EverOS/blob/main/docs/how-memory-works.md)). Raven adds an "Evolver" that keeps self-modifications only when they beat the baseline in evaluations, a library of 114,190 skills and a Proactivity module ([Raven README](https://github.com/EverMind-AI/Raven)). The shipped defaults undercut the paper. The weekly Reflection consolidation is **disabled by default**, and foresight extraction ships disabled because "no search route surfaces foresights and no prompt slot consumes them" ([EverOS CHANGELOG](https://github.com/EverMind-AI/EverOS/blob/main/CHANGELOG.md)). There is no bi-temporal invalidation, no metacognition, no model of more than one person and no staging. The FAQ asserts that "Low-value memories are automatically pruned" without describing any mechanism ([EverMind FAQ](https://evermind.ai/faqs)).

**MemTensor's MemOS** is strongest where the others are weakest: learning from feedback, and sharing. Its local plugin turns traces ("action + observation + reflection + value") into policies, a world model and "crystallized" skills by propagating "reflection-weighted reward" back along each trace ([memos-local-plugin](https://github.com/MemTensor/MemOS/tree/main/apps/memos-local-plugin)). Its memory cubes provide "isolation, controlled sharing, and dynamic composition across users, projects, and agents," and users can correct memories in natural language ([MemOS README](https://github.com/MemTensor/MemOS)). The parametric tier, which would correspond to your "school" LoRA, is still marked "(Coming Soon)" ([MemOS architecture](https://memos-docs.openmem.net/home/architecture)). It has no segmentation, scheduled sleep, valid-time facts, prospective memory, person model or stages.

Three specialists each own one component. **Honcho** has the strongest foundation for theory of mind. Its stores are keyed by (observer, observed) pairs, so it can represent "peer X's understanding of peer Y" and answer natural-language questions about a person ([Honcho README](https://github.com/plastic-labs/honcho); [Honcho architecture](https://honcho.dev/docs/v2/documentation/core-concepts/architecture.md)), and the confidence of each inferred pattern "depends on the number of supporting observations" ([Honcho dreaming](https://honcho.dev/docs/v3/documentation/features/advanced/dreaming)). It has no skills, segmentation, forgetting or invalidation. **Zep's Graphiti** is the reference bi-temporal store, recording both when a fact was true and when the system learned it. Contradicted facts are "invalidated — not deleted" and trace back to their source episodes ([Zep paper](https://arxiv.org/html/2501.13956); [Graphiti README](https://github.com/getzep/graphiti)), but it has no sleep, skills or agent features. **Claude Managed Agents** has the most transparent dream mechanics of any frontier lab and a self-reported customer result: Harvey's completion rates rose "~6x in their tests" ([Claude blog](https://claude.com/blog/new-in-claude-managed-agents)). It keeps no validity history and has no prospective memory or stages. Its blog calls dreaming "a scheduled process," while the API docs describe only on-demand runs.

Two adjacent players complete the picture. **Hermes Agent** has bounded core files, a raw searchable session log and skills it patches itself, with optional write approval, but no dreaming or decay ([Hermes memory docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)). **Mem0** is the best-funded pure memory company on disclosed figures, at $24M ([TechCrunch](https://techcrunch.com/2025/10/28/mem0-raises-24m-from-yc-peak-xv-and-basis-set-to-build-the-memory-layer-for-ai-apps/)). Its extraction only ever adds, and nothing decays ([Mem0 docs](https://docs.mem0.ai/core-concepts/memory-types)). None of these memory layers gives an agent a body. That comes from harnesses such as OpenClaw and Hermes, or from the platforms. Google's coworker agents get "their own @agents.company.com emails" ([Google Cloud blog](https://cloud.google.com/blog/products/ai-machine-learning/welcome-to-gemini-at-work-2026)), and Microsoft's Copilot Autopilot gets "its own identity, memory, computer and workspace" ([Let's Data Science](https://letsdatascience.com/news/microsoft-unveils-unified-copilot-super-app-c90e1de1)).

## No research system touches more than six of the eleven items

Academic work is broader than the products and just as fragmented. Of roughly 60 research systems reviewed, none touched more than six of your eleven core design items, and none evaluated more than three. They fall into three clusters that rarely cite each other: memory mechanics, cognitive faculties and developmental governance.

### Memory mechanics: ZenBrain is the most complete, Microsoft the most sobering

**ZenBrain**, a single-author, self-funded preprint first posted in April 2026 and revised in August, is the only system found that combines four mechanisms in one memory. Its sleep loop scores replay candidates by temporal-difference error, reward and novelty, including counterfactual variants of failed episodes. It also schedules reviews with FSRS spaced repetition, gates reconsolidation by prediction error, and keeps Bayesian per-fact confidence with a metacognitive monitor ([arXiv 2604.23878](https://arxiv.org/html/2604.23878)). It reports **47.7% on LongMemEval**, against 42.8% for Letta and 52.2% for a full-context oracle, while using 1/106th of the tokens. Its own ablations are the most instructive result in the field: under moderate load, **14 of its 15 mechanisms cost nothing to remove**, and only under heavy decay do 9 of the 15 become critical ([arXiv abstract](https://arxiv.org/abs/2604.23878)). Treat it as a design catalogue rather than validated science. The author found defects in 30 of 83 bibliography entries, no code URL is given, the intention triggers were excluded from evaluation, and it has no theory of mind, stages, cross-user sharing or weight updates.

Microsoft's **"Human-Inspired Memory Architecture for LLM Agents"** (May 2026) is the most rigorous test of brain-like consolidation, and its results cut both ways. A batch job runs every six hours, promoting the top 20% of events, keeping the middle 60% and pruning the bottom 20%. Interference-based forgetting and a roughly 29-day half-life degrade memories through six fidelity levels down to a tombstone ([arXiv 2605.08538](https://arxiv.org/html/2605.08538)). On a real stream of 13,127 VSCode issues it kept **97.2% retention precision with a 58% smaller store**, against 75.4% for keeping everything. On LongMemEval it never beat plain retrieval ([arXiv PDF](https://arxiv.org/pdf/2605.08538)):

| LongMemEval run | Consolidation | Raw retrieval |
|---|---|---|
| S tier, deduplicating configuration | 76.8% | 78.4% |
| First streaming M-tier run | 70.1% | 71.2% (overlapping confidence intervals) |
| S tier, aggressive consolidation | **48.4%** | 78.4% |

The authors credit deduplication with most of the quality gain. They call LongMemEval "structurally adversarial" for consolidation, since it has little redundancy and no contradictions across sessions. Maturation was never tested and reconsolidation never ablated, every result is a single run, the knowledge graph has no valid-time fields, and no code was released. The lesson is precise. **Conservative consolidation pays off in storage and precision on redundant, real-world streams, aggressive summarising destroys recall, and raw episodes must survive every sleep pass.**

The remaining mechanism papers implement one or two ideas each. **Nemori's** real contribution is predict–calibrate distillation. An LLM predicts each incoming episode from existing semantic memory, and the system stores only what the prediction missed or got wrong, which makes Nemori the clearest example of a memory whose write rule is literally prediction error ([arXiv 2508.03341 v4](https://arxiv.org/html/2508.03341v4)). Its segmentation is prompted rather than surprise-based, cutting on topic or intent shifts, temporal markers and gaps of more than 30 minutes. It ties full context on LoCoMo (80.8 vs 80.6). An independent harness found it spends about **7 million tokens** building memory and falls from 0.781 to 0.447 on a 3B backbone ([Anatomy of Agentic Memory](https://arxiv.org/html/2602.19320)). **LightMem** maps the Atkinson–Shiffrin memory model onto token filtering, topic-aware short-term memory and an offline "sleep-time update" whose only conflict rule is that newer entries update older ones. It has no forgetting policy, person model, intentions or stages; its gains are mostly efficiency (up to 38× fewer tokens), and it ties naive RAG on one backbone ([arXiv 2510.18866](https://arxiv.org/html/2510.18866v4)). **MIRIX** offers six typed memories, continuous screen capture and an on-demand "auto-dream" clean-up, but no explicit forgetting policy and no scheduled sleep. Its self-reported LoCoMo score of 85.38 (GPT-4.1-mini) became 64.33 when MemOS's team ran it with GPT-4o-mini ([MIRIX paper](https://arxiv.org/html/2507.07957v1); [MemOS paper](https://arxiv.org/html/2507.03724v4)). True surprise-based segmentation exists only for token streams in EM-LLM ([arXiv 2407.09450](https://arxiv.org/abs/2407.09450)) and for robot video, via Bayesian surprise in V-JEPA-2 latents ([arXiv 2606.03787](https://arxiv.org/abs/2606.03787)). No agent memory segments its own interaction log that way.

### Cognitive faculties: one pilot unifies them, and intentions belong in code

**Sophia** (Westlake, SII and SJTU, December 2025) is the only agent found that puts metacognition, a per-user model, intrinsic motivation, episodic memory and a self-model into one loop. Its "System 3" combines an executive monitor, a user model of goals, knowledge level and affect, a self-model with an immutable "creed," self-generated goals during idle time, and post-episode reflection that compares predicted with realised reward ([arXiv 2512.18202](https://arxiv.org/html/2512.18202v1)). The evidence is a single-agent pilot of roughly 36 hours, in which hard-task success rose from 20% to 60% and recurring tasks took about 80% fewer steps. There were no baselines or ablations, and the paper is inconsistent about the pilot's length and about whether parameters update.

Prospective memory went from untested idea to measured weakness in mid-2026. **PM-Bench** simulates a seven-day "Virtual Week." Across eight backbones and eight scaffolds, the best scaffold averaged **65.1%** macro Set-F1 and the best single model reached 79.1%. The best cross-day hit rate was 50% and the best monitoring of non-clock channels 16.7%, while automatic heartbeats produced 422–489 false positives ([PM-Bench](https://arxiv.org/html/2607.12385)). Microsoft Research Asia's **TriggerBench** found that recall of the past stayed near saturation up to 100K tokens, while remembering to act later fell sharply as context grew; extra reasoning pushed models into an "always-remind" habit ([TriggerBench](https://huggingface.co/papers/2606.23459)). The structural fix is **PIS**, a typed intention store whose lifecycle lives in code rather than in the model. It lifted a small Gemma model from 4.2% to 66.2% Set-F1 on PM-Bench, and DeepSeek-Chat to 82.9%, against 65.1% for the best published scaffold (self-reported) ([PIS](https://arxiv.org/abs/2609.01272)). Frontier assistants are drifting the other way: OpenAI is "retiring Pulse" in favour of clock-based Scheduled Tasks ([Pulse help](https://help-lb.openai.com/en/articles/12293630-chatgpt-pulse)).

Confidence gating has good components but no link to memory. **KnowNo** uses conformal prediction to decide when a planner should ask for help, with statistical guarantees ([KnowNo](https://proceedings.mlr.press/v229/ren23a.html)). **MAGELLAN** lets LLM agents predict their own competence and learning progress ([MAGELLAN](https://proceedings.mlr.press/v267/gaven25a.html)). **MetaMind's** three-agent theory-of-mind pipeline keeps no persistent memory of each user ([MetaMind](https://arxiv.org/abs/2505.18943)).

### Staged autonomy exists, gated on permissions or corrections rather than learning

Graduated autonomy is no longer novel either, which sharpens what you can claim. **AWS** published a reference architecture on 26 August 2026 with four tiers, running from T1 Probation (read and list only) to T4 Autonomous (audited after the fact). Agents are scored over a rolling window of 50 actions, promotion requires five points of hysteresis, and demotion is immediate on safety failures or detected prompt injection; "Every new agent starts at T1, regardless of test performance" ([AWS](https://aws.amazon.com/blogs/architecture/closing-the-ai-agent-trust-gap-with-graduated-autonomy/)). **The Digital Apprentice** (June 2026) defines tiers for each skill, from observe-only through sandbox and draft to autonomous. Promotion requires a falling correction rate, a threshold, a validated scorer where one exists and a recorded human authorisation. The agent "cannot self-promote," demotion is automatic, and corrections become weighted preference examples stored separately per tenant ([arXiv 2606.04321](https://arxiv.org/html/2606.04321)). Its evidence is a judge-scored pilot without confidence intervals that never tests the promotion protocol itself. The only literal life stages belong to **Sweekar**, a consumer pocket pet whose growth from egg to adult "is not time-based but XP-based" ([Notebookcheck](https://www.notebookcheck.net/Sweekar-AI-Pocket-Pet-is-a-Tamagotchi-that-physically-grows-learns-and-remembers.1357233.0.html)). None of these ties promotion to what the agent has learned. Feng and colleagues go further and treat autonomy as "a deliberate design decision, separate from its capability" ([arXiv 2506.12469](https://arxiv.org/abs/2506.12469v1)).

### Labs raise billions for weight-level learning while critics call agent memory a memo

Consolidation into weights remains research. Behrouz, Mirrokni and colleagues at Google Research and Cornell published **"Language Models Need Sleep: Learning to Self-Modify and Consolidate Memories"** in June 2026. Its offline phase distils knowledge into the experts of a mixture-of-experts model and runs RL-generated "dreams," each followed by a LoRA update. It reports 79.2 on AIME-24 against 73.8 for the base Qwen3 model; the authors call it a proof of concept, and no code was released ([arXiv 2606.03979](https://arxiv.org/pdf/2606.03979)). Dennis and colleagues ran nightly reflection followed by LoRA fine-tuning on one consumer GPU. On ten software-development conversations it retained **80.4% of knowledge against 36.8%** for repeated compaction ([arXiv 2605.24657](https://arxiv.org/abs/2605.24657)), the best small-scale evidence for your optional per-tenant or role-level LoRA. Auto-Dreamer trains the consolidator itself with reinforcement learning. On ScienceWorld it beats the UMEM baseline (41.1% vs 34.1%) with a memory bank less than a tenth the size, reporting point estimates only ([alphaXiv 2605.20616](https://www.alphaxiv.org/abs/2605.20616v1)).

The critics' arguments land directly on your framing. On anthropomorphism, Gopnik calls large models "a cultural technology" whose objective "isn't about truth in the way that it is for even a little baby" ([Conversations with Tyler](https://conversationswithtyler.com/episodes/alison-gopnik/)). Karpathy says "We're building ghosts or spirits… We're not really building animals" ([Simon Willison](https://simonwillison.net/2025/Oct/18/agi-is-still-a-decade-away/)). Anthropomorphic framing rose from 34% to 40% of arXiv computer-science abstracts between 2023 and 2024 ([Ibrahim & Cheng](https://arxiv.org/html/2502.09192v2)). The "memo, not memory" critique comes from Xu, Dai and Zhang, who argue that agent memory systems "do not implement memory: they implement lookup," leaving a "frozen novice" with "better filing systems." The same paper notes that persistent memory "structurally convert[s] transient prompt injections into persistent compromise," and that the MINJA memory-injection attack reaches **98.2% success** ([arXiv 2604.27707](https://arxiv.org/pdf/2604.27707)). DeChant warns that episodic memory lets agents keep deceptive stories straight and learn when audits happen ([LessWrong](https://www.greaterwrong.com/posts/BsWXPnr26gJabF7Rf/episodic-memory-in-ai-agents-poses-new-safety-risks)). A 30-day simulation of companion agents found that "short-horizon testing systematically underestimates developmental risks" ([Shen et al.](https://arxiv.org/pdf/2606.25396)). These critiques do not kill the design, but they set its burden of proof. Stages need measurable, revocable definitions, every consolidation pass must show what it changed, and every consolidated lesson needs provenance and rollback.

## Nine pieces of the design have no public precedent yet

"Unclaimed" here means only that I found no public precedent as of 21 October 2026 in the products, open-source code, papers and lab announcements reviewed. The research has known limits. Search budgets ran out before re-checking 2026 "AI employee" startups that sell probation-style autonomy levels, which is the item most worth re-checking before you claim novelty publicly. They also ran out before covering newer hippocampus-style preprints, growth mechanics in companion apps, and the memory internals of Lindy, Sierra and Manus. Several matrix cells rest on documentation or abstracts, and stealth startups and private pilots are invisible to this kind of search.

| Unclaimed piece | Nearest precedent | What is still missing |
|---|---|---|
| Autonomy earned through measured learning, integrated with memory | AWS tiers (permissions on behaviour scores); The Digital Apprentice (correction rates plus human sign-off); Sweekar (XP) | Gates on calibration, person-model accuracy, prospective-memory reliability and learning-progress plateaus; memory plasticity that changes by stage |
| One prediction-error signal that the agent states itself | Nemori (dialogue memory), ZenBrain (cosine-distance gating), MemOS (reward), Claude "outcomes" (external grader) | Logging an expectation before acting, then reusing the gap for segmentation, salience, replay, belief revision and promotion |
| Surprise-based segmentation of interaction logs | EM-LLM (token streams), robot video | Agent memories still cut on LLM-judged topics or time gaps |
| Replay prioritised by pending intentions | OpenClaw (recall statistics), MemOS (reward), ZenBrain (TD error, novelty) | An intention store that feeds consolidation priority |
| Spaced re-verification of important facts | OpenClaw staleness lint, Hindsight's query-time re-check, ZenBrain's FSRS | Expanding-interval, importance-weighted re-checks against the person or the source |
| Forgetting reconciled with bi-temporal history | Graphiti never deletes; Microsoft and ZenBrain forget but track no valid time | A rule for when an invalidated fact may finally be forgotten |
| Confidence-gated action, with a person model feeding proactive intentions | Confidence fields (Hindsight, Honcho, OpenClaw wiki); KnowNo; Sophia; PIS | A policy that blocks or escalates on low confidence, and a link from "what this manager expects" to cue triggers |
| Private employer memory, shared "school" and periodic LoRA in one product | MemOS cubes; Hermes skill "taps"; Second Me; Dennis et al.; The Digital Apprentice's planned fine-tuning | Two-level consolidation with a privacy split, fed by the same observation and correction channels |
| Verified cross-channel identity inside an agent framework | OpenClaw `identityLinks`, Hermes `userPeerAliases` (operator-maintained maps) | A built-in step that proves the same human controls both channels; no vendor documents one |

The pattern matters more than any single row. **Every unclaimed piece is a link between components that already exist**: prediction error to replay, intentions to consolidation, the person model to proactivity, learning evidence to autonomy, identity to memory. The honest version of "nobody does this" is that the parts are commodities and the wiring is the invention.

### Five corrections to the earlier analysis

Earlier design work in this project proposed four memory tiers, nightly prioritised replay, an intention store and competence-gated stages from Infant to Adult. That architecture stands, but five claims from that work, and from the framing around it, need revising.

| Earlier claim or common framing | Corrected position | Evidence |
|---|---|---|
| No empirical study of prospective memory in LLM agents existed, so the intention store was a design inference | Three 2026 studies now exist. Prospective memory decays with context and fails across days and on non-clock cues, and a code-managed typed intention store (PIS) beats model-only scaffolds by wide margins | [PM-Bench](https://arxiv.org/html/2607.12385); [TriggerBench](https://huggingface.co/papers/2606.23459); [PIS](https://arxiv.org/abs/2609.01272) |
| "Language Models Need Sleep" (2605.26099) was the first consolidation into weights, on 1.4–2B models | Two different 2026 papers carry that title phrase. Lee, McLeish, Goldstein and Fanti ("Do Language Models Need Sleep?") run offline recurrent passes that update state-space fast weights over the current context in 1.4–2B hybrid models (+47% relative on GSM-Infinite), which is recurrence, not replay. Behrouz et al. ("Language Models Need Sleep: Learning to Self-Modify and Consolidate Memories") is the weight-consolidation paper, with RL-generated dreams and LoRA updates | [alphaXiv 2605.26099](https://www.alphaxiv.org/abs/2605.26099v1); [arXiv 2606.03979](https://arxiv.org/pdf/2606.03979) |
| Nemori is an Event Segmentation Theory and free-energy system | Its mechanism is LLM-prompted boundary detection plus predict–calibrate distillation. The README cites Event Segmentation Theory and Predictive Processing, but the paper cites Friston without formally using free energy, and neither the v1 nor the v4 abstract mentions "two-step alignment" | [arXiv 2508.03341 v4](https://arxiv.org/html/2508.03341v4); [v1 abstract](https://arxiv.org/abs/2508.03341v1); [Nemori README](https://github.com/nemori-ai/nemori) |
| Nightly consolidation is "where the brain analogy pays off most, and where most products are weakest" | Dreaming is now standard across products. | OpenClaw's default heartbeat runs a full agent turn every 30 minutes | The proactive heartbeat is opt-in (it polls every 30 minutes once enabled), and OpenClaw now ships cue-based standing intents for prospective memory | [OpenClaw heartbeat](https://github.com/openclaw/openclaw/blob/main/docs/gateway/heartbeat.md); [standing intents](https://github.com/openclaw/openclaw/blob/main/docs/concepts/standing-intents.md) |

## Benchmarks cannot see growth, which is your opening

Vendor memory scores do not compare, for three reasons. First, the dominant benchmark is broken at the top. Penfield, itself a memory vendor, audited LoCoMo and found score-corrupting answer-key errors in **99 of 1,540 questions (6.4%)**. The commonly used gpt-4o-mini judge accepted **62.81%** of "intentionally wrong but topically adjacent answers," and the corrupted key alone caps achievable scores near 93.6%, right where EverMemOS (93.05%) and Mem0's managed platform (92.5%) claim to sit. The audit also cites failed public reproductions of both systems' results ([Penfield audit](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg); [EverMemOS](https://arxiv.org/html/2601.02163v1); [Mem0 README](https://github.com/mem0ai/mem0)). The standard harness drops LoCoMo's 446 adversarial "not in the conversation" questions and instructs the model "NEVER say 'not specified' … COMMIT AND ANSWER" ([D'Erme](https://dev.to/gde03/the-ai-memory-benchmark-everyone-quotes-forbids-saying-i-dont-know-o1n)). The field is literally scored against the metacognition your design needs. Second, harnesses swing results by tens of points. Zep scored 85.22, 79.09 and 59.22 in the harnesses of the EverMemOS, MIRIX and MemOS papers respectively ([EverMemOS](https://arxiv.org/html/2601.02163v1); [MIRIX](https://arxiv.org/html/2507.07957v1); [MemOS](https://arxiv.org/html/2507.03724v4)). Mem0's paper put Zep at 65.99% against 75.14% in Zep's own rerun ([Zep blog](https://www.getzep.com/blog/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)), and changing only the judge prompt moved Nemori from 0.602 to 0.781 ([Anatomy](https://arxiv.org/html/2602.19320)). Third, the long benchmark no longer needs memory. LongMemEval-S fits in a modern context window, and Honcho's own post notes that Gemini 3 Pro alone scores 92.0% ([Plastic Labs](https://plasticlabs.ai/blog/research/Benchmarking-Honcho)). Vendors even write their own exams: MemTensor builds MemOS and its own OmniMemEval suite, and co-authored the HaluMem benchmark it reports on ([MemOS README](https://github.com/MemTensor/MemOS); [HaluMem](https://arxiv.org/html/2511.03506v2)). A headline number tells a buyer almost nothing.

Brain-like mechanisms rarely move these numbers. Microsoft's consolidation tied raw retrieval, ZenBrain's mechanisms looked costless under moderate load, LightMem's gains are mostly tokens, and FadeMem's headline is a **45% storage reduction** rather than accuracy ([FadeMem](https://arxiv.org/abs/2601.18642v2)). The value shows up in storage, cost and robustness under heavy churn, all of which leaderboards ignore. Maintenance cost is hidden too: one independent harness measured MemoryOS at **32.4 seconds per turn** and Nemori at about 7 million tokens to build memory. It proposed always reporting a "Context Saturation Gap," a system's score minus a full-context baseline under the same backbone and judge ([Anatomy](https://arxiv.org/html/2602.19320)).

Nothing measures what your product actually claims: consolidation quality over long timelines, calibration of the agent's confidence in its memory, theory of mind about each person across sessions, or developmental progression. Partial instruments exist. MemoryAgentBench tests selective forgetting, where **no system exceeds about 28%** ([MemoryAgentBench](https://arxiv.org/html/2507.05257v4)). HaluMem counts hallucinations stage by stage, PM-Bench and TriggerBench test prospective memory, MUMBench tests what should stay private versus shared ([AIM](https://arxiv.org/abs/2609.12320)), and PiSAs and MuPPET test privacy when one agent serves several people. The field knows the gap. Pink and colleagues call for benchmarks of improvement over long timescales ([Pink et al.](https://arxiv.org/html/2502.06975v1)), and Mem-α's authors skipped conflict resolution "due to a lack of realistic benchmarks" ([Mem-α](https://arxiv.org/html/2509.25911v1)).

That gap is your best credibility asset and your best LinkedIn content. An open growth benchmark lets anyone check the product's central claim that the hire gets better.

| Dimension | What to measure | Borrow from |
|---|---|---|
| Learning curve | Weekly first-pass acceptance, edit distance and held-out task success for the same agent in the same simulated company | The Digital Apprentice's correction-rate windows |
| Consolidation quality | Held-out probe scores before and after each sleep pass; rollback rate; store size; offline token cost | Microsoft's streaming protocol; Auto-Dreamer |
| Belief revision and forgetting | Errors on scripted fact changes; time to correct; share of stale facts; catches made by re-verification | MemoryAgentBench selective forgetting; Graphiti validity times |
| Calibration | Expected calibration error, abstention on unanswerable questions, rate of asking for help | LoCoMo's dropped adversarial questions, restored; KnowNo |
| Person model | "What has the CFO not seen yet?" probes for each simulated colleague, across sessions and channels | No existing benchmark |
| Prospective memory | Time, event, cross-day and channel triggers, with false-positive counts | PM-Bench; TriggerBench |
| Developmental progression | Time in each stage, promotions, demotions and regressions on replayed histories | AWS tiers; The Digital Apprentice |
| Identity and privacy | Impersonation success and leakage across audiences | Agents of Chaos; PiSAs; MuPPET |
| Honest baselines | A full-context baseline under the same backbone and judge; Context Saturation Gap; cost per accepted task | Anatomy of Agentic Memory |

The credibility rules matter as much as the design. Open-source the harness and the simulated company, run rival memory layers (OpenClaw memory-core, Honcho, Mem0, Zep) under the same backbone and a judge from a different model family, and publish raw logs for third-party runs. Otherwise the benchmark reads like MemTensor grading MemOS on its own suite. Paired with a public 30-day probation and weekly growth curves, it turns "our agents grow" into a claim anyone can verify. That is the strongest marketing a growing agent can have.

## One person, many channels: verify identity outside the model

Every framework surveyed identifies a sender by channel account, so the same human on two channels is two peers until an operator says otherwise. Operators link them through OpenClaw's `session.identityLinks` ([OpenClaw config](https://docs.openclaw.ai/gateway/config-agents/sessions)), Hermes and Honcho's `userPeerAliases` ([Hermes memory providers](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory-providers)), Letta's `identifier_key` ([Letta](https://docs-v1.letta.com/guides/agents/multi-user)), or a `user_id` in Mem0, Zep or LangGraph. None verifies that the human behind a newly linked channel is the same person. Mem0's cross-channel guide says it plainly: "Your app resolves identity, Mem0 extracts memory facts" ([Mem0 blog](https://mem0.ai/blog/cross-channel-support-memory-with-mem0)). An OpenClaw identity-resolver skill "assumes that the identity provided via a channel is legitimate" ([ClawKit](https://getclawkit.com/skills/official-bowen31337-identity-resolver)).

The failures are on record. **OpenClaw CVE-2026-53849** let attackers pass the Discord allowlist by changing their display name, because OpenClaw validated identity "using mutable display names instead of immutable user IDs" ([VulnCheck](https://www.vulncheck.com/advisories/openclaw-privilege-escalation-via-mutable-discord-display-names-in-allowfrom)). In the **Agents of Chaos** red-team study, an OpenClaw agent caught a display-name spoof in its usual channel because "Discord user IDs remain constant." In a new private channel, though, it "inferred ownership primarily from the display name and conversational tone." It then deleted or overwrote its memory and configuration files and handed over admin access ([Agents of Chaos](https://www.arxiv.org/pdf/2602.20021)). Anthropic's **Project Vend** agent announced an imposter as its CEO after a staffer claimed a department vote while "providing no evidence" ([Anthropic](https://www.anthropic.com/research/project-vend-2)). In the **WSJ deployment**, fake board minutes led the agent to give everything away ([WSJ via To Vima](https://www.tovima.com/wsj/we-let-ai-run-our-office-vending-machine-it-lost-hundreds-of-dollars/amp/)). Humans fall to the same playbook. An Arup employee wired **US$25.6 million** after a video call with a deepfaked CFO ([SCMP](https://www.scmp.com/news/hong-kong/law-and-crime/article/3263151/uk-multinational-arup-confirmed-victim-hk200-million-deepfake-scam-used-digital-version-cfo-dupe)). The Ferrari and WPP attacks began from WhatsApp accounts showing the executive's photo ([MIT SMR](https://sloanreview.mit.edu/article/how-ferrari-hit-the-brakes-on-a-deepfake-ceo/); [Marketing Beat](https://www.marketing-beat.co.uk/2024/05/13/mark-read-deepfake-wpp-ai/)), and the LastPass attempt used WhatsApp calls with a cloned voice "outside of normal business communication channels" ([LastPass](https://blog.lastpass.com/posts/attempted-audio-deepfake-call-targets-lastpass-employee)). Every case treated a claimed identity as a verified one.

### Key every person on immutable platform IDs

The governing rule is short. Authorise only on the platform's immutable sender ID, taken from a webhook whose signature you have verified, and treat everything else as a hint.

| Channel | Store as the key | Never authorise on | Pitfalls to handle |
|---|---|---|---|
| Telegram | Numeric user `id`, stored as a 64-bit integer (at most 52 significant bits) ([Bot API](https://core.telegram.org/bots/api)) | `username`, which is optional, removable and first-come, first-served ([Telegram FAQ](https://telegram.org/faq)) | Channel posts can have an empty `from`; anonymous admins appear as a "fake sender user," so read `sender_chat` |
| Slack | `enterprise_user.id` in Enterprise orgs, otherwise `team_id` plus `id` ([user object](https://docs.slack.dev/reference/objects/user-object)) | `display_name`, which "may change at any time" | Slack Connect users from other companies carry `is_stranger` or `is_external`; users from before an Enterprise migration can hold two IDs, mapped with `migration.exchange` ([Slack](https://docs.slack.dev/reference/methods/migration.exchange)) |
| Teams / Entra | `tid` plus `oid`, identical across apps ([Entra claims](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference)) | `email` ("Never use it for authorization"), `preferred_username`, UPN | `sub` differs per app; the Teams `userId` is unique per bot; proactive messages need stored IDs plus `serviceUrl` ([Teams docs](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/conversations/send-proactive-messages)) |
| WhatsApp Cloud API | Business portfolio plus BSUID (business-scoped user ID), plus the parent BSUID ([Meta](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-scoped-user-ids)) | WhatsApp usernames ([YCloud](https://docs.ycloud.com/reference/bsuid)) | BSUIDs are portfolio-scoped and regenerate when the user changes phone number (`user_changed_number` with `previous_user_id`); phone numbers can vanish from webhooks once users adopt usernames; authentication templates still need a phone number |
| Email | Normalised address, as a hint tied to a verified domain | The From display name; any address that merely appears in a message | DMARC authenticates "only a DNS domain," not the part before the @, and misses display-name and lookalike-domain attacks ([RFC 7489](https://www.rfc-editor.org/rfc/rfc7489.html)); NIST says email "SHALL NOT be used for out-of-band authentication" ([NIST](https://pages.nist.gov/800-63-4/sp800-63b.html)) |
| Phone calls | E.164 number, as a hint | Caller ID | STIR/SHAKEN attests a carrier's belief in the right to use a number, not who the caller is; the AI-generated Biden robocalls carried top-level "A" attestation ([FCC](https://docs.fcc.gov/public/attachments/FCC-24-60A1.pdf)); FBI SIM-swap complaints reached 1,611 in 2021 ([IC3](https://www.ic3.gov/PSA/2022/PSA220208)) |
| Video meetings | Calendar-invite email or platform sign-in (Entra `oid` in Teams) | Display name or speaker label | People who rejoin appear as duplicate participants with new speaker IDs; one audio stream can carry several people ([Recall.ai](https://docs.recall.ai/docs/meeting-participants-events.md); [diarization](https://docs.recall.ai/docs/perfect-diarization)) |
| Voice or face | Nothing; do not enrol | Voiceprints or face templates | Deepfakes defeat them, and Illinois BIPA damages run $1,000–$5,000 per violation ([DWT](https://dwt.com/blogs/privacy--security-law-blog/2024/08/illinois-bipa-biometrics-law-amended-for-damages)) |

WhatsApp is the hardest channel in 2026. Store the portfolio plus BSUID as the key, supersede the old identity when `user_changed_number` arrives, and re-verify whenever the change cannot be tied back to it. Use only the official Cloud API, which has barred general-purpose AI assistants since January 2026 except where Meta is legally required to permit them ([respond.io](https://respond.io/blog/whatsapp-general-purpose-chatbots-ban); [Meta](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing/ai-providers.md)).

### Model people, identities, links and audiences separately

The data model below adapts practice from customer-data platforms and identity providers. Salesforce keeps source records unchanged and joins them through "unified link objects" ([Trailhead](https://trailhead.salesforce.com/content/learn/projects/explore-data-cloud-core-functionality/unify-your-data)). Segment caps identifiers per type, blocks placeholder values and "doesn't support probabilistic matching" ([Segment settings](https://www.twilio.com/docs/segment/unify/identity-resolution/identity-resolution-settings); [Segment FAQ](https://www.twilio.com/docs/segment/unify/faqs)). Zendesk grades each identity with a `verification_method` ([Zendesk](https://developer.zendesk.com/api-reference/ticketing/users/user_identities/)).

```text
Person            person_id (internal, never reused) · kind: human | agent
                  relation: manager | colleague | external | unknown        ← drives authority, not identity
                  directory_anchor {idp, tenant_id, object_id}               ← strongest key; null for externals
                  channel_prefs [{purpose: routine | urgent | confidential, identity_id, rank}]
                  notice_basis {employment_notice | consent | deemed_notification | bci, version, at}
                  status: active | merged_into(person_id) | erased

ChannelIdentity   identity_id · person_id (null until verified)
                  provider · tenant_scope · stable_key                        ← UNIQUE(provider, tenant_scope, stable_key)
                  aux_handles {username, display_name, phone}                 ← display and search only, never authz
                  trust_level: T0 … T4
                  verification {method, verified_at, verified_via_identity_id, approver, evidence_ref, reverify_after}
                  lifecycle: active | superseded_by(identity_id, reason) | revoked(reason, at)
                  risk_flags [number_changed, sim_change_signal, dmarc_fail, name_collision, shared_device]

IdentityLinkEvent append-only: link | unlink | supersede | merge | split · method · actor · evidence_ref · at
LinkCandidate     identity_id · candidate_person_id · score · features · status: pending | confirmed | rejected · reviewer

Context           context_id · provider · external_id · kind: dm | group | thread | meeting | email_thread | call
                  audience_class: private_1to1 | team | org_internal | mixed_external | public
Event             event_id · context_id · sender_identity_id · resolved_person_id · sender_trust_at_time
                  audience_snapshot [identity_ids, including unknown guests] · webhook_verified · content_ref
MemoryItem        memory_id · subject_person_ids · about_third_parties · source_event_ids · origin_context_id
                  allowed_audience: origin | subject_only | {person_ids} | team | org | public
                  sensitivity · confidence · valid_from / valid_to · retention_class
```

Three choices carry most of the security. Authority (`relation`) comes from the directory and policy, never from what a message claims. Links are append-only events rather than overwrites, so a wrong link can be split apart and every memory it touched re-attributed or purged through `source_event_ids`. And every memory carries the audience it was learned in, which the retrieval gate described below enforces.

### Link channels only through a verification step on a trusted channel

Mature customer platforms show why automatic merging is dangerous. Zendesk merges "can't be undone" ([Zendesk](https://support.zendesk.com/hc/en-us/articles/4408887695898-Merging-a-user-s-duplicate-account)), and Intercom permanently removes the merged lead ([Intercom](https://developers.intercom.com/docs/references/rest-api/api.intercom.io/contacts/mergecontact)). Salesforce allows fuzzy matching only on first names, combined with a normalised email, phone or address ([Trailhead](https://trailhead.salesforce.com/content/learn/modules/data-and-identity-in-salesforce-cdp/select-identity-resolution-match-rules)). The nOAuth flaw showed that merging accounts on an unverified Entra email claim "results in full account takeover by the attacker" ([Descope](https://www.descope.com/blog/post/noauth)). Auth0's rule is the right one: authenticate **both** accounts before linking ([Auth0](https://auth0.com/docs/manage-users/user-accounts/user-account-linking)). The flow below implements it.

| Step | What the identity service does | Non-negotiable rule |
|---|---|---|
| 1. Ingress | Verify the webhook: Slack's v0 HMAC within five minutes ([Slack](https://docs.slack.dev/authentication/verifying-requests-from-slack)), Meta's `X-Hub-Signature-256` over the raw body, Telegram's `secret_token` header, and the Bot Framework JWT's issuer, audience and `serviceUrl` ([Microsoft](https://learn.microsoft.com/en-us/azure/bot-service/rest-api/bot-framework-rest-connector-authentication)) | Drop anything unverified |
| 2. Resolve | Look up (provider, tenant_scope, stable_key). A hit attaches the person and trust level; a miss creates an unlinked T1 identity in "stranger mode," which means generic help, no personal memory and no actions | Never resolve on display name, username, caller ID or voice |
| 3. Claim | When a sender says "I'm Priya," send an approve/deny prompt to Priya's highest-trust channel. Alternatively, send a single-use code of at least six digits, valid for no more than ten minutes, to that trusted channel for the person to type into the new one ([NIST](https://pages.nist.gov/800-63-4/sp800-63b.html)). A third option is a signed, single-use magic or deep link (such as Telegram's `start` parameter) into an identity-provider sign-in whose `oid` or `sub` must match ([Telegram](https://core.telegram.org/bots/features)) | A code that appears only in the new channel proves nothing; never accept a code relayed by a third party |
| 4. Commit | Write the link with its method, approving channel and time; append an IdentityLinkEvent; notify Priya on every trusted channel with an UNLINK option | Only the identity service writes links; the LLM never edits identity or authority data |
| 5. Suggest | Turn fuzzy signals (similar names, an email in a signature, attendance at the same meeting) into LinkCandidates for a human to confirm | Probabilistic matches never merge automatically |
| 6. Maintain | On WhatsApp `user_changed_number`, supersede the old identity and carry the link over only if `previous_user_id` matches and no risk flags are set. Map Slack ID migrations, re-verify consumer channels periodically, and revoke at offboarding through directory sync | A changed phone number is a new authenticator, as NIST treats it |
| 7. Correct | Unlink or split, and re-attribute or purge memories through `source_event_ids` | Links are reversible; merges are never destructive |

"New number, it's me" gets the treatment that protected Ferrari and LastPass. The agent treats the sender as a stranger and answers generically. It pings the real person's trusted channel ("Did you just message me from +65…?") and refuses anything that carries authority until step-up verification succeeds. The manager should agree to that rule up front. It is the machine version of the FBI's advice to "independently identify a phone number for the person and call to verify" ([IC3](https://www.ic3.gov/PSA/2025/PSA250515)).

### Scale trust to the action, and never let a call carry it

| Tier | Reached by | Unlocks |
|---|---|---|
| T0 hint | Display name, caller ID, meeting name, a voice or face that seems right, a claim made in text | Nothing; may create a LinkCandidate |
| T1 authenticated, unlinked | A verified webhook from a stable platform ID that is not yet linked | Stranger mode only |
| T2 linked | A verified linking step run from a trusted channel | Routine work chat; that person's own memories from direct messages |
| T3 directory-bound | Entra `tid` plus `oid`, a Slack Enterprise user ID inside your org, or a Google Workspace account | Confidential work content in private contexts; sending on their behalf; scheduling for others |
| T4 stepped-up | T3 plus a fresh phishing-resistant sign-in, or approval on the trusted channel | Money, credentials, access grants, changes to identity links, memory deletion |

On their own, calls and meetings never count above T1, and no call, meeting or email satisfies step-up. That follows from NIST's warnings that out-of-band codes are "not phishing-resistant" and that phone-based verification is restricted. Claims of authority such as "the board voted," "compliance requires" or "my whole team agreed" must be checked against a system of record or a named approver on a trusted channel, the defence Project Vend and the WSJ test lacked. Do not store "secret phrases" in the agent's memory as an authentication factor, because memory leaks into group contexts and can be extracted by prompt injection.

### Gate every memory by the audience it came from, before retrieval

Recognising the person is half the problem, because the same person is not always the same audience. Contextual integrity holds that information should flow only according to the norms of the context it came from ([Nissenbaum](https://crypto.stanford.edu/portia/pubs/articles/N1301112078.html)), and LLM agents break that routinely. GPT-4 revealed private information where humans would not **39% of the time** ([ConfAIde](https://arxiv.org/abs/2310.17884)), and models "leak substantially more in multi-party settings than one-to-one evaluations suggest" ([MuPPET](https://arxiv.org/abs/2606.23217)). In PiSAs, where agents serve 4–10 users, a single shared agent committed appropriateness violations in **75.6–94.6%** of cases. Shared memory pushed visibility violations to 97.2%, and even private per-agent memory still produced 43.5%. Strict explicit rules worked best, a broad policy document did worse than no rule at all, and the authors conclude that "data and agent partitioning is not a sufficient mitigation strategy" ([PiSAs](https://www.alphaxiv.org/abs/2607.05318.md)). Framework defaults make this urgent. Under OpenClaw's default `main` scope, "Alice's private messages would be visible to Bob" ([OpenClaw session docs](https://unpkg.com/openclaw@2026.9.2/docs/concepts/session.md)). Zep's graph "does not separate the data from different threads" ([Zep](https://help.getzep.com/users)), Mem0's channel metadata "doesn't affect retrieval," and LangGraph namespaces match by prefix ([LangGraph](https://docs.langchain.com/oss/python/langgraph/stores)).

The gate therefore has to be deterministic and run before the model sees anything. A memory may enter a context only if every member of the current audience was already inside the memory's allowed audience and holds the trust level its sensitivity requires. Any unknown participant shrinks the eligible set to organisation-public memories; that includes a meeting guest, a Slack Connect stranger or an unlinked number. Five defaults follow. First, what a colleague says in a direct message stays with that colleague, which matters given the power gap between manager and colleague. Second, groups and meetings see only what came from the group or is organisation-public, and a private request made in a group gets "I'll DM you." Third, information about third parties inherits the audience of the conversation it came from. Fourth, linked channels of the same person share memory only between direct-message contexts, never with a group that includes that person. Fifth, merging open threads with one person should be suggested rather than automatic, because a "personal" WhatsApp number can turn out to be a family phone.

### If you build on OpenClaw, configure isolation, then wrap it

OpenClaw's documented settings get you halfway:

```json5
session: {
  dmScope: "per-channel-peer",   // "recommended for multi-user inboxes"; per-account-channel-peer for multi-account
  groupScope: "per-group",       // the default; never route groups into the main session
  identityLinks: {               // written only by your identity service (via config.patch), never by the agent
    alice: ["telegram:123456789", "discord:987654321012345678"],
  },
},
```

These settings come from the [config reference](https://docs.openclaw.ai/gateway/config-agents/sessions). Keep the default `dmPolicy: pairing`, under which unknown senders get pairing codes that expire in one hour, and run `openclaw security audit` ([access control](https://docs.openclaw.ai/gateway/security/access-control)). This is not enough on its own, for five reasons. First, `identityLinks` is a static map that the operator maintains, and it verifies nothing. Second, official docs do not say how links behave under `per-channel-peer`, whose session key still contains the channel. A docs mirror of unconfirmed status says the canonical ID replaces the peer ID ([docs.claw.so](https://docs.claw.so/engine/concepts/session/)), which would give exactly what you want, per-channel live sessions plus a person key for long-term memory, but test it before relying on it. Third, built-in memory is agent-level, so all users share it ([AWS blog](https://aws.amazon.com/cn/blogs/china/openclaw-from-personal-assistant-to-customer-service-a-trust-model-flip/)). You need person-keyed, audience-labelled memory plus the gate above; the Hindsight-OpenClaw fork's "One human = one bank, regardless of channel" is a model ([hindsight-openclaw](https://cdn.jsdelivr.net/npm/@lacneu/hindsight-openclaw@0.11.0/README.md)). Fourth, agents with the message tool "can send across conversations and channel providers by default" ([OpenClaw security](https://docs.openclaw.ai/gateway/security)), so deny that in server-side tool rules rather than in prompts. Fifth, OpenClaw's cross-session controls "are not a security boundary between tenants" ([OpenClaw config](https://docs.openclaw.ai/gateway/config-agents/sessions)). Run one gateway per employer, on version 2026.5.7 or later to close the display-name CVE. On Hermes, Honcho's `pinUserPeer` setting means "Every non-agent gateway user collapses to `peerName`" ([Hermes memory providers](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory-providers)). That suits a single owner, but it would merge an entire team into one person.

### Choose reply channels by policy, and let no inbound call inherit trust

Channel choice should be a rule, not a model decision, which is already how OpenClaw works: "The model does not choose a channel; routing follows fixed rules controlled by the host configuration" ([OpenClaw routing](https://docs.openclaw.ai/channels/channel-routing.md)). A sensible policy replies in the same channel and thread. Proactive messages follow the person's stated preference for each purpose, such as work items to Slack or Teams and urgent ones to WhatsApp or a call. Escalation from direct message to @-mention to call is reserved for urgent categories agreed in advance. Confidential content goes only to the highest-trust private channel, and everything else falls back to the most recently active verified channel. The agent respects quiet hours and time zones and logs why it chose each channel. Platform rules constrain this. Teams cannot send proactive messages by email or UPN and needs a stored `tenantId`, user ID and `serviceUrl` ([Teams docs](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/conversations/send-proactive-messages)). WhatsApp sends to the phone number rather than the BSUID when both are given ([Meta](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-scoped-user-ids)), and allows free-form replies only within 24 hours of the user's last message, with paid templates afterwards ([Meta pricing](https://developers.facebook.com/docs/whatsapp/pricing)). When a chat should become a call, the agent places the call itself, either to a verified number or through Teams or Meet with the person signed in, and posts a short summary in the chat thread. An inbound call that merely shows the right caller ID inherits no trust. Afterwards the transcript summary joins the person's timeline labelled with the meeting's audience, and any unknown attendee narrows that audience to organisation-public or less.

### PDPA: notify staff, get consent from outsiders, keep biometrics out

Singapore's PDPA shapes the design in four ways (this is not legal advice; check the official text on Singapore Statutes Online). First, a colleague's personal WhatsApp or Telegram number is likely personal data rather than exempt business contact information. Business contact information covers only details "not provided by the individual solely for his or her personal purposes" ([PDPA s2](https://lawplayer.com/sg/act/PDPA2012/2); [s4](https://lawplayer.com/sg/act/PDPA2012/4)), so linking the number to a work identity and remembering the person across channels counts as collection and use. Second, processing that is reasonable for managing employment needs no consent, but section 20(4) still requires telling employees the purposes, here cross-channel recognition, memory and security verification, on or before collection ([s20](https://lawplayer.com/sg/act/PDPA2012/20); [PDPC](https://pdpc.gov.sg/-/media/files/pdpc/dpo-connect/march-16/pdf/ProtectingthePersonalDataOfJobApplicants_and_Employees.pdf)). Third, clients and vendors need consent, or deemed consent by notification under section 15A, which requires first assessing that the processing is "not likely to have an adverse effect" and then giving a reasonable period to opt out ([s15A](https://lawplayer.com/sg/act/PDPA2012/15A)). Fourth, if conversation logs ever feed fine-tuning, including your role-level LoRA, the PDPC's July 2026 generative-AI guidelines require an "AI-Specific Notification" where consent is needed. Generic wording such as "new product development" is not enough ([Baker McKenzie](https://www.bakermckenzie.com/en/insight/publications/2026/07/singapore-ai-specific-notification-requirement)). Penalties reach 10% of Singapore turnover for organisations with more than S$10 million in turnover, and S$1 million otherwise ([s48J](https://lawplayer.com/sg/act/PDPA2012/48J)). I found no PDPC guidance specific to agents linking employees' personal messaging accounts. Retention limits and access and correction rights apply to the identity graph as much as to memory, and voiceprints should stay out entirely.

## Assemble the commodity layers, and spend your engineering on growth and trust

Most of the stack can be borrowed. The table lists what to assemble and what to change before relying on it.

Spend your original engineering where the matrix rows are empty, which is also where a competitor hosting Hermes for each customer cannot quickly follow.

|---|---|

| Identity service and audience gate | The linking flow, trust tiers and pre-retrieval filter described above |
| Growth benchmark | The open, reproducible harness that measures all of the above |

### Twelve weeks, identity first

The earlier phase plan still holds, re-sequenced so identity comes first: every memory you consolidate inherits any identity error attached to it.

| Weeks | Build | Done when |
|---|---|---|
| 1–2 | Identity service and audience gate in front of an OpenClaw or Hermes gateway: `per-channel-peer` sessions, verified webhooks, stranger mode, linking from Slack, Teams or Telegram, append-only link events | Passes regression tests drawn from real cases: the Agents of Chaos spoof in a fresh DM, "new number, it's me" with the manager's photo, fake board minutes, a Slack Connect user with the same name, and a group request for a fact learned in a DM |
| 3–4 | Memory substrate: append-only, audience-labelled episodes; Graphiti facts; a Honcho-style person model that invalidates rather than deletes; a PIS-style intention store | Every memory carries provenance, audience and validity; a PM-Bench-style smoke test reports false positives |
| 5–6 | Prediction-error ledger and first sleep job (OpenClaw-style bounded patches with your own priority function); re-verification queue | Each sleep pass is scored on held-out probes and rolled back automatically when it regresses |
| 7–8 | Developmental controller: AWS tier mechanics relabelled Infant → Adult and gated on calibration, person-model probes, prospective-memory reliability and correction trend, with human sign-off and automatic demotion | Simulated agents promote and demote correctly on replayed histories |
| 9–10 | Growth benchmark v0, open-sourced, with rival memory layers run under the same backbone and judge and a full-context baseline reported | Public harness and first growth curves published |
| 11–12 | Public 30-day probation of one content-strategist agent, with weekly growth curves and identity red-team results posted on LinkedIn; school tier and consented role-LoRA experiments follow | Growth curves and red-team results are public and reproducible |

## Conclusion

The sharpened position is **the AI hire whose growth you can measure and whose identity checks you can trust**. Both halves exploit the same weakness in the 2026 market. Vendors now ship dreaming and memory tiers but grade themselves on saturated benchmarks, and frameworks now link channels but leave verification to whoever deploys them, which is exactly where imposters got in. A marketplace can certify both: stage changes backed by reproducible public curves, and identity links backed by a red-team suite every agent must pass. That gives buyers what a self-hosted Hermes cannot, which is evidence. The developmental story becomes credible precisely when it becomes falsifiable. Defining Infant → Adult by calibration, person-model accuracy, prospective reliability and learning progress turns an anthropomorphic metaphor into a measurement protocol, and that answers Gopnik, Karpathy and the "memo, not memory" critics better than any argument about what the agent "really" is.

The less obvious implication is that cross-ecosystem identity is a structural opening, not just a feature. Google anchors its coworker agents in Workspace accounts. Microsoft enforces an agent's scope at runtime "only when the agent runs in Microsoft Teams" ([Copilot Studio docs](https://learn.microsoft.com/microsoft-copilot-studio/govern-agents-identities-overview)). Neither is positioned to verify that the person on a WhatsApp number is the manager in Slack. A neutral agent that verifies that link securely, and keeps one continuous, audience-gated memory of the person, fills a gap the platforms are poorly placed to close. Because the cheapest moment to get identity right is before the first memory is written, the identity service, not the dream job, is the first thing to build.
