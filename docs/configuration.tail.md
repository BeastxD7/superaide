## How to enable

**Impostor simulator (local testing only).** Off by default. To try impostor scenarios from the operator console, put `ENABLE_SIMULATOR=true` in `backend/.env` (uncomment the line in the example), restart the API, then open `/console` with your `ADMIN_TOKEN` and use the Simulator page. Never turn it on on a public server.

**Models and keys.** Set `ANTHROPIC_API_KEY` (or let each owner connect their own in Workspace, Connections) and Ava replies for real; without a key she runs offline and spends nothing. `MODEL_CHAT`, `MODEL_TRIAGE`, `MODEL_DEEP` choose models; a model missing from `brain/pricing.py` is refused. Spend is capped by `MAX_SPEND_USD` (lifetime), `BUDGET_DAILY_USD`, `BUDGET_MONTHLY_USD` and `BUDGET_DAILY_BY_BUCKET`, per Ava. Other providers (Ollama, OpenAI-compatible, and so on) are connected in the app, then used as `<preset>::<model>`; on `DEPLOY_MODE=hosted` owner-typed private addresses are refused. Local thinking models (for example `qwen3:8b` on Ollama) answer directly: Ava turns their thinking off, and reasoning text never appears in a reply on any channel. Ollama also cuts every prompt to its context window, 4096 tokens unless set, silently; Ava's prompt is about 8,000, so she would forget who she works for. Superaide asks Ollama (the window in use from `/api/ps` when the model is loaded, else the Modelfile's from `/api/show`; unknown means no warning) and warns you in the app and in Check my setup when the model's window is under 12,288, with the fix: a Modelfile with `FROM qwen3:8b` and `PARAMETER num_ctx 16384`, then `ollama create qwen3-16k -f Modelfile`, then choose `qwen3-16k` on the AI model page (the window cannot be set through Ollama's OpenAI-compatible endpoint).

**Context windows (#641).** Every model has a window in code: Claude and the known hosted models from a table (`brain/context_window.py`), an Ollama model from the server, an unknown hosted model 32,768 and an unknown local one 4,096. The owner can set one by hand in the provider's `meta` (`context_window`, or `context_windows` per model). The input budget is the window minus the room for the answer minus 10%. After each reply Superaide compares the prompt tokens the server counted with what it sent; if the server counted far fewer it cut the prompt, which is written to the audit trail (`prompt_truncated`, once per model per six hours), shown in the app banner and in Check my setup, and told to the owner once a week at most.

**Fitting the prompt to the window (#641).** Before each model call Superaide checks the prompt against the input budget. What does not fit is dropped by rule, never by the model: older history first (oldest first, down to the last four turns), then notes found automatically for the latest message (lowest ranked first; the `recall` tool can still fetch them), then the last four turns, then long results of tools already run this turn. The charter and safety rules, who is speaking, the audience and trust lines, pending approvals and waiting people, the tool definitions and the latest message are never dropped, and nothing is ever added. Every trim writes an audit row `prompt_trimmed` with counts only (what was dropped, before and after in tokens, the window and where it came from). If the fixed parts alone are over the budget the row says by how much (`over_budget_by`): on a very small window that is what the compact and minimal prompts are for. Claude and other large-window models are not affected.

**Prompt tiers (#641).** Ava's full prompt is about 5,000 tokens before any history, which is slow and too big for a small window. Code picks one of three sizes per turn from the model's window and the message, never the model: *full* for windows of 100k tokens or more (Claude and the big hosted models; unchanged, and a hosted model nobody described keeps it too), *compact* for 8k to 100k (about 1,500 tokens of fixed prompt; three to six tools chosen from the message and the state, such as the inbox and relay tools when someone is waiting, with only the rules for those tools and about 1,500 tokens of history) and *minimal* for windows under 8k or a greeting with nothing pending on a window under 100k (about 600 tokens, no tools, the last two turns). The charter and the limits on what Ava may do herself are in every tier; who is speaking, the audience filter, taint and approvals are decided by the same code in every tier, a channel keeps exactly its shared tools, and a tool that was not offered is refused if the model calls it anyway. The owner brief and the capability block are left out of the compact and minimal prompts (notes still arrive through recall). The tier and the tools offered are written to the audit trail (`prompt_tier`). `tests/evals/test_prompt_size_gate.py` measures each part per tier and fails when compact goes over 2,500 tokens, minimal over 600, or the full prompt grows more than 5% over `backend/evals/prompt-size-baseline.json`.

**Google sign-in, Calendar and Gmail.** One OAuth client of type "Web application" serves all three.
1. In Google Cloud enable the Google Calendar API and the Gmail API, and add the scopes `calendar.readonly`, `calendar.events`, `gmail.readonly`, `gmail.compose`.
2. Register redirect URIs `<FRONTEND_ORIGIN>/api/auth/google/callback` (sign-in) and `<FRONTEND_ORIGIN>/api/app/connections/google/callback` (Calendar). Other origins you use go in `GOOGLE_REDIRECT_ORIGINS` and must also be allowed by `LINK_ORIGINS` or `DEV_ORIGINS`.
3. Set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, then `GOOGLE_SIGNIN_ENABLED=true` for sign-in. Calendar and Gmail need no flag for chat use: the owner clicks Connect Google in Connections and the token goes to their vault.
4. Gmail triage: also `TRIAGE_ENABLED=true` and `GMAIL_TRIAGE_ENABLED=true`. Calendar push: `PUBLIC_BASE_URL=https://...` with `/webhooks/*` routed to the API, then `GOOGLE_CALENDAR_PUSH=true`.

**Telegram.** Create a bot with @BotFather and connect the token in the app, or set `TELEGRAM_BOT_TOKEN`. Polling needs nothing else. For webhooks set `TELEGRAM_WEBHOOK_BASE_URL` (or `PUBLIC_BASE_URL`) to your https address and route `/webhooks/*`; `TELEGRAM_WEBHOOK_SECRET` is for the single env-configured bot.

**Slack.** Create the app from [`slack_manifest.yml`](../backend/src/superaide/channels/slack/manifest.yml) (Socket Mode), then connect it in the app or set `SLACK_BOT_TOKEN` (`xoxb-`), `SLACK_APP_TOKEN` (`xapp-`), `SLACK_SIGNING_SECRET` and `SLACK_TEAM_ID` (people from other workspaces count as external). The bot needs these scopes: `app_mentions:read`, `chat:write`, `im:history`, `im:read`, `im:write`, `users:read`, and `channels:history` + `groups:history` so Ava reads the thread when you @-mention her in one (always on, never stored), and `files:read` so she can read a PDF or text file you or someone she knows sends (read in memory, never stored; photos are acknowledged but not looked at). At startup and when you connect, Ava checks the granted scopes: a missing one is logged as an ERROR and shown on Connections and in a banner, and only the part that needs it stops (a thread is then answered without being read). Add the scope under OAuth & Permissions and reinstall the app.

**Email (SMTP).** `MAIL_BACKEND=smtp`, `MAIL_FROM`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_SECURITY` (`starttls` / `ssl` / `none`). Then `REQUIRE_VERIFIED_EMAIL=true` if hiring should need a confirmed address. `MAIL_BACKEND=log` (the default) writes each email, **including live verification and password-reset links**, to the API log: fine on your own machine, never on a shared or public server.

**Many owners or one.** `ALLOW_MANY_OWNERS=true` (default) lets anyone who signs up hire their own isolated Ava. `false` makes the first account to hire Ava the only owner. On a public server also keep `DEPLOY_MODE=hosted` so sign-ups never run on your keys (the compose file forces this).

**Voice and push.** `VOICE_INTRO_V2=true` for the conversational introduction call (free with the browser's speech). Add `DEEPGRAM_API_KEY` and/or `ELEVENLABS_API_KEY` for better voices, or let owners save theirs. `PUSH_ENABLED=true` for web push (use a real `VAPID_SUBJECT`).

**Switches that are not booleans.** `APPROVAL_BINDING` (`off` / `record` / `strict`, default `strict`: a send whose content changed after the owner saw it is blocked), `APPROVAL_TTL_HOURS` (0 = approvals never expire), `STEPUP_MODE` (`confirm` / `password`), `EMBEDDER` (`local` / `voyage` / `fake` / `none`; `voyage` sends private facts to Voyage AI), `DEPLOY_MODE` (`self_hosted` / `hosted`), `MAIL_BACKEND` (`log` / `smtp`), `VOICE_PROVIDER`, `VOICE_ASR` and `VOICE_TTS`, `THIRD_PARTY_MESSAGE_RETENTION_DAYS` (0 = keep forever).

**Which flags are safe.** Safe to switch on yourself: bounded cost, no data leaves your server, nothing irreversible. Owner decision: it spends money, sends data to another company, makes something public, or widens what Ava may do without asking. The grouping is in the index at the top of `backend/.env.example` ("Safe to turn on by yourself" and "Needs an owner decision first"). Features whose routes are gated answer 404 while off.

## Production differences

`.env.prod.example` (copied to `.env` next to `docker-compose.prod.yml`, or filled in by `deploy/bootstrap.sh`) is a shorter file for the container stack ([deploy/README.md](../deploy/README.md)):

- Required: `DOMAIN`, `POSTGRES_PASSWORD`, `APP_DB_PASSWORD`, `SECRETS_MASTER_KEY` (back it up; without it saved keys cannot be decrypted) and `ADMIN_TOKEN`. The compose file refuses to start without them.
- Fixed by the compose file whatever `.env` says: `DATABASE_URL` (the app's own role, so Row-Level Security applies), `MIGRATION_DATABASE_URL` (empty), `FRONTEND_ORIGIN` (`https://DOMAIN`, or `PUBLIC_URL`), `SESSION_COOKIE_SECURE=true`, `DEPLOY_MODE=hosted`, `ENABLE_SIMULATOR=false`, `ENABLE_API_DOCS=false`, and `RUN_JOBS_IN_API` / `RUN_CHANNELS_IN_API` `false` (a separate worker runs them).
- Only in this file: `HTTP_PUBLISH`, `HTTPS_PUBLISH` (host ports for Caddy) and `PUBLIC_URL` (when the public address is not `https://DOMAIN`).
- It lists only the common settings. Every other variable in `backend/.env.example`, including all the feature flags above, can be added to the same `.env` and is passed to the api and worker.
- Keys in this file are never used for an owner on `hosted`: owners connect their own model, Telegram and Slack in the app. The exceptions are `PLATFORM_KEY_OWNER_EMAILS` (the operator's own Ava) and Superaide AI credits.
- Web container variables (`API_INTERNAL_URL`, `TRUST_PROXY_HEADERS`) are set by the compose file; the full frontend list is in `frontend/.env.example`.
